# HTTP/1.1 / HTTP/2 / HTTP/3 的区别

## 核心回答（面试口述版，1 分钟能讲完）

HTTP/1.1 一个 TCP 连接同时基本只服务一个请求，后面的要排队，这叫队头阻塞。页面只能开 6 个左右连接做并发。
HTTP/2 还是 TCP，但改成二进制分帧，一条连接里多路复用很多流。头用 HPACK 压。TCP 丢一个包，整条连接的流都停，队头阻塞下沉到传输层。
HTTP/3 把 TCP 换成 QUIC（跑在 UDP 上）。流之间独立，丢包只伤一条流。TLS 1.3 揉进 QUIC，首次 1 RTT，复用能 0 RTT。
切网时 QUIC 用 Connection ID，IP 变了连接还能续。TCP 五元组一变就断。
面试一句话：1.1 应用层排队，2 解决应用层但 TCP 仍堵，3 用 QUIC 把堵在流上切开。

## 展开

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 传输层协议 | TCP | TCP | **QUIC (UDP)** |
| 多路复用 | 无，**队头阻塞**：同一 TCP 连接一次只处理一个请求 | **二进制分帧**：一个 TCP 连接多流并行；但 **TCP 层仍队头阻塞**（丢包全流停） | 基于 QUIC：流独立，丢包只影响对应流，**彻底解决队头阻塞** |
| 头部压缩 | 纯文本，重复很多 | **HPACK**（静态表 + 动态表 + 哈夫曼） | **QPACK**（适配 QUIC 乱序） |
| 服务器推送 | 无 | Server Push（用得少，Chrome 已废弃） | 支持 / 看实现 |
| 握手耗时（含 TLS） | TCP 3 次握手 + TLS ≈ 3 RTT；会话复用可 1 RTT | 同左 | QUIC 集成 TLS1.3：首次 **1 RTT**，复用 **0 RTT** |
| 连接迁移（切网） | 五元组变化连接就断 | 同左 | **连接 ID** 标识，IP/端口变也不中断 |
| 兼容性 | 100% | 浏览器基本全支持 | 较新，还在铺开 |

1.1 还有 keep-alive、管道化（基本被废弃，因为队头阻塞）。2 的 Server Push Chrome 2022 就摘了，别当卖点。3 在 CDN 边缘已经很常见（Cloudflare、阿里云都开）。

## 延伸

- 相关题：TCP 队头阻塞、TLS 握手 RTT、CDN 已开 h3。
- 对比题：同源 6 个连接是浏览器限制，RFC 没写死。HTTP/3 不是「HTTP/2 跑在 UDP 上」，帧格式和 QPACK 都不一样。
- 面试加码：Server Push 别当卖点，Chrome 已摘。防火墙拦 UDP 会降级到 h2。切网靠 Connection ID。

## 常见追问

- Q: 什么是队头阻塞？HTTP/2 在哪些层面还存在队头阻塞？
  A: 前面一个请求（或一个包）卡住，后面的全等。1.1 发生在应用层：连接上前一个响应没完，后一个发不了。2 用流把应用层解开了，但 TCP 要保证顺序，中间一个包丢了，后面已经到达的包也不能交给 HTTP/2，所有流一起等重传。这是传输层队头阻塞。3 的 QUIC 按流编号独立重传，才把这层也拆掉。

- Q: QUIC 为什么能用 UDP 做可靠传输？
  A: UDP 本身不可靠。QUIC 在 UDP 之上自己实现：流 ID、序号、重传、拥塞控制（Cubic/BBR）、流量控制。相当于把 TCP 的可靠性和 TLS 1.3 的加密重写成用户态协议，丢包处理按流来，握手也少一轮。防火墙拦 UDP 时浏览器会降级到 HTTP/2。

## 自己的易错点 / 之前答崩过的地方

我说 HTTP/2 已经没有队头阻塞。追问 TCP 丢包就把我问穿了。
把 HTTP/3 说成「HTTP/2 跑在 UDP 上」。帧格式、头压缩（QPACK）、握手都不一样。
1.1 的 6 个连接限制我当成协议写死的。那是浏览器的同源连接上限，RFC 没写 6。
