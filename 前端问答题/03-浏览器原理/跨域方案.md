# 跨域（CORS）和跨域解决方案

## 核心回答（面试口述版，1 分钟能讲完）

同源策略：协议、域名、端口都相同才算同源。`http://a.com:80` 和 `https://a.com`、`http://a.com:81` 都跨域。
受限制的是 JS 读结果：AJAX / fetch / DOM 访问。`<img>` `<script>` `<link>` `<video>` 这些标签可以跨域加载，只是 JS 读不了内容。
现在正规做法是 CORS：服务端在响应头里放行 Origin。带自定义头、PUT/DELETE、JSON Content-Type 会先发 OPTIONS 预检。
带 cookie 时 `Access-Control-Allow-Origin` 不能是 `*`，必须写成具体域名，再加 `Allow-Credentials: true`。
开发环境常用 webpack/vite 代理或 nginx 反代，浏览器看来是同源。
JSONP 只用 GET，靠 `<script>` 不受同源限制，老项目还能见到。

## 展开

1. 同源策略的定义（协议 / 域名 / 端口 三同）。哪些操作受限制？哪些不受？（<img>/<script>/<link>/<video> 不受限制）

三同才同源。子域 `a.b.com` 和 `b.com` 也不同源。
受限：`XMLHttpRequest` / `fetch`、不同源窗口的 DOM、读跨域图片像素（canvas 污染）、LocalStorage 按源隔离。
不受限：标签加载资源、CSS 里的 `@font-face` 有时另有 CORS 要求。跨域脚本能跑，但报错栈和内容 JS 读不到（除非 CORS）。WebSocket 不受同源限制，但握手可校验 Origin。

2. **CORS**（主流方案）：简单请求 / 预检请求（OPTIONS）的区别、触发预检的条件、关键响应头（Access-Control-Allow-Origin / Allow-Methods / Allow-Headers / Allow-Credentials / Max-Age）

简单请求：GET/HEAD/POST，头只在 CORS 安全集合里（Accept、Content-Type 为 `text/plain` / `multipart/form-data` / `application/x-www-form-urlencoded`）。浏览器直接发，响应里要有 `Access-Control-Allow-Origin`。
否则先 OPTIONS 预检。服务端回：
- `Access-Control-Allow-Origin: https://a.com`（或 `*`，但不能同时带凭证）
- `Allow-Methods: PUT, DELETE`
- `Allow-Headers: Content-Type, Authorization`
- `Allow-Credentials: true`（要带 cookie 时）
- `Max-Age: 600`（预检结果缓存秒数）

浏览器把预检过了才发真请求。

3. **JSONP**：原理、为什么只能 GET、手写实现思路

页面动态插 `<script src="http://api.com/data?callback=cb">`。服务端返回 `cb({...})`，当作脚本执行。script 没有同源限制，所以能拿数据。script 只能 GET，失败也没有 HTTP 状态可读，且等于把执行权交给对方，有 XSS 风险。现在别新写。

4. **其他方案**（知道原理就行）：nginx 反向代理、node 中间件代理、postMessage、WebSocket、document.domain、location.hash、window.name

- 反代：浏览器打同域 `/api`，网关转发给后端，Origin 在服务端消失。
- `postMessage`：跨窗口通信，一定要校验 `event.origin`。
- WebSocket：握手是 HTTP，之后不受同源，服务端自己看 Origin。
- `document.domain` 只能降到父域，且已废弃。
- `location.hash` / `window.name` 是老 iframe 黑客技巧，了解即可。

## 常见追问

- Q: CORS 的预检请求具体会发什么？怎么响应才过？
  A: 方法 OPTIONS，头里有 `Origin`、`Access-Control-Request-Method`、`Access-Control-Request-Headers`。响应 204/200，带上 Allow-Origin（和请求 Origin 对上）、Allow-Methods（包含那个方法）、Allow-Headers（包含那些自定义头）。要带 cookie 再加 Allow-Credentials，Origin 写死具体值。缺一个浏览器就拦真请求，控制台报 CORS error，Network 里往往只看见 OPTIONS。

- Q: `Access-Control-Allow-Credentials: true` 时 Origin 能写 `*` 吗？
  A: 不能。规范禁止。必须回具体 Origin，比如 `https://a.com`。前端 fetch 还要 `credentials: 'include'`，否则 cookie 不带出去。两边缺一不可。

## 自己的易错点 / 之前答崩过的地方

我以为跨域请求浏览器根本没发出去。其实简单请求发出去了，JS 读不了响应；预检失败才拦住真请求。
本地开发 CORS 配了 `*`，一上 cookie 登录就挂。改成白名单 Origin + credentials。
把「端口不同」忘了，`localhost:3000` 打 `localhost:8080` 也是跨域。
