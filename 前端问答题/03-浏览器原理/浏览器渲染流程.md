# 浏览器渲染流程（HTML → 像素）

## 核心回答（面试口述版，1 分钟能讲完）

渲染进程拿到 HTML 后，主线程做这些事：解析 HTML 建 DOM，解析 CSS 建 CSSOM，合成分 Render Tree，Layout 算位置和大小，Paint 生成绘制指令，Composite 把图层交给 GPU 合成上屏。
JS 能改 DOM/CSS，所以碰到同步脚本会暂停解析。
CSS 会阻塞首次渲染，也会挡住它后面的同步脚本（脚本可能读样式）。
改几何（宽高、位置、字体）走重排再重绘；改颜色只重绘；改 `transform` / `opacity` 往往只走合成。
动画用 `transform` 能放到合成线程，少占主线程。

## 展开

1. 五步走：HTML 解析 → DOM → CSSOM → Render Tree → Layout（布局/重排）→ Paint（绘制/重绘）→ Composite（合成）

更细一点其实是六段：Parse HTML → Parse CSS → Render Tree → Layout → Paint → Composite。Render Tree 是 DOM 和 CSSOM 的交汇。后续任何改动都可能从中途重跑，不一定从头开始。

2. 每一步的输入、输出是什么？

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 解析 HTML | 字节流 | DOM 树 |
| 解析 CSS | CSS 文本（外链 + 内联 + UA 样式） | CSSOM |
| 合成 Render Tree | DOM + CSSOM | 可见节点树（跳过 `display:none`，`visibility:hidden` 还在） |
| Layout | Render Tree | 每个节点的几何信息 |
| Paint | 布局结果 | 绘制记录（背景、边框、文字、图） |
| Composite | 图层绘制结果 | 屏幕上的帧 |

3. 什么情况下会触发重排 / 重绘 / 合成层加速？

重排：改尺寸、位置、字体、增删 DOM、改 `display`，读 `offsetHeight` 这类几何值也可能强制刷布局。
重绘：改 `color`、`background`、`visibility`、`outline`。
合成：节点有自己的图层，改 `transform`、`opacity` 只让合成线程动。`will-change: transform`、3D、`position:fixed`、`<video>`、`<canvas>` 容易提升为层。层太多反而吃内存。

4. GPU 合成层（Compositing Layer）是什么？哪些属性会直接触发合成（transform / opacity）？

把页面拆成若干纹理，由合成线程（和 GPU 进程）按图层叠起来。主线程忙着跑 JS 时，合成线程仍能靠已有图层做 transform 动画。常见提升条件：`transform` 不是 none、`opacity` 小于 1 的动画、`will-change`、`filter`、`position: fixed` 在部分浏览器。只写一行 `transform: translateZ(0)` 老办法强行提升，现在更推荐 `will-change` 用完再去掉。

5. 为什么说 `transform: translate()` 比 `left/top` 动画更高效？

`left/top` 改的是布局信息，每帧重排 + 重绘 + 合成。`transform` 在合成层上做，布局树不动，主线程可以空出来。移动端尤其明显，少掉帧。

## 延伸

- 相关题：重排重绘、输入 URL 全过程、脚本 defer/async。
- 对比题：改 `left/top` 走布局，改 `transform` 往往只合成。`display:none` 不进 Render Tree，`visibility:hidden` 还占位。
- 面试加码：首屏 CSS 尽早、尽量小。合成层过多会吃内存，`will-change` 用完删掉。

## 常见追问

- Q: `<script>` 标签放 `body` 末尾和加 `defer` / `async` 的区别？
  A: 放 body 末尾：解析已经到尾巴，DOM 基本好了，但仍是同步下载+执行，会推迟 DCL。`defer`：并行下载，解析完按顺序执行，DCL 等它。`async`：谁下完谁执行，和 DOM 顺序无关，适合独立统计脚本。模块脚本默认 defer。现在更常见 `type="module"` 或打包后一个 defer 包。

- Q: CSS 会阻塞 HTML 解析吗？会阻塞渲染吗？
  A: 现代浏览器 HTML 解析和 CSS 下载是并行的，CSS 不直接停 HTML tokenizer。但它阻塞**渲染**（没有 CSSOM 不敢画，避免无样式闪烁）。同步脚本如果插在 stylesheet 后面，脚本执行会等 CSSOM，表现为解析也被拖住。所以首屏 CSS 要尽早、尽量小。

## 自己的易错点 / 之前答崩过的地方

我把 `display:none` 和 `visibility:hidden` 当成一回事。none 不进 Render Tree，hidden 占位还在，仍走布局。
「GPU 加速一定更快」我不加条件就说。图层爆炸、大面积 `will-change` 会更卡。
脚本放底部我以为等于 defer。defer 能并行下载，放底部还是解析到了才开始拉。
