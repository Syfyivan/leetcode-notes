# 二分查找：一套模板，边界定生死

> 这份笔记和回溯篇一样，记的是一套通用骨架加一把判断的尺子，不是每题背一个模板。
> 二分和回溯的难点正好相反：回溯难在想不到枚举结构，二分难在边界差一个 `=` 就死循环或漏解。
> 涉及题目：[搜索插入位置](../搜索插入位置.js)（LC35，二分母题）、[搜索二维矩阵](../搜索二维矩阵.js)（LC74，精确查找）、[在排序数组中查找元素的第一个和最后一个位置](../在排序数组中查找元素的第一个和最后一个位置.js)（LC34，lower_bound 复用）、[搜索旋转排序数组](../搜索旋转排序数组.js)（LC33，两段有序）。

> 历史彩蛋：世界上第一个二分查找 1946 年发表，第一个没 bug 的版本 1962 年才出现，隔了 16 年。Knuth 说很多程序员写不对。所以觉得难是正常的，它是出了名的看着简单、写对极难。

## 一、二分是什么：猜数字游戏

在有序序列里找东西，每次把范围砍一半，`O(log n)` 定位目标。前提是必须有序（升序或降序），无序不能二分。

像猜数字：1~100 猜我心里的数，只告诉你大了还是小了。不从 1 挨个试，而是每次猜中点、砍掉一半。100 个数最多 7 次（2⁷>100），100 万个数只要 20 次，威力全在砍半。

机器用两个指针 `left`/`right` 框住还没排除的范围，`mid` 取正中：

```
一轮循环干三件事：
  1. 算中点   mid = (left + right) / 2
  2. 看中点   比较 nums[mid] 和 target
  3. 砍一半   挪 left 或 right → 范围缩小一半
不停重复，直到范围砍空（left 撞上 right）
```

## 二、核心心法：不要偷看邻居抓现行

这是二分最反直觉、也是新手最大的坑，和回溯的门卫心法同源。

新手本能是站在 `mid`，探头看左右邻居（`nums[mid+1]`、`nums[mid-1]`），判断自己是不是正好站在答案上。这个思路是很多 bug 的源头：

1. “我在答案旁边”的情况有无穷多种，每种都要单独 return，每种都可能 off-by-one；
2. 邻居可能越界（mid 在边缘时 `nums[mid+1]` 是 `undefined`，判断失灵）；
3. 一旦某种情况没 return，指针不动就死循环。

正确心法和回溯“局面是门卫自动拼出来的”一样：我不需要在任何一步知道答案在哪，只维护一条规则，每砍一刀都不砍掉答案，砍到范围只剩一条缝，答案自己现身。

把数组想成一条红蓝染色带，找黑白交界点：

```
nums:  [1,   3,   5,   6]     target = 5
染色:   白   白   黑   黑      ← "nums[i] >= target 吗"
             ↑白  ↑黑
            要找的：第一个黑格（下标2）
```

- 我从不问自己是不是正好在缝上，那就是偷看邻居；
- 只保证 `left` 待在白区、`right` 待在黑区，每轮缩小空隙；
- 最后 `left` 和 `right` 在缝上撞头，答案被逼出来。

答案是“不停砍、不砍错”这条规则自动逼出来的，不是某一步看出来的。你负责定规则，收敛交给循环，全程只碰 `nums[mid]`，不看邻居、不加额外边界检查。

## 三、主力模板：左闭右开 lower_bound（背下来）

所有“找第一个满足条件的位置”的题，都是这个模板换个 `check` 条件，35、34、旋转数组全靠它。

```javascript
var searchInsert = function (nums, target) {
  let left = 0;
  let right = nums.length; // 注意是 length，不是 length-1

  while (left < right) {
    // 左闭右开 [left, right)，空区间就停
    const mid = Math.floor((left + right) / 2);
    if (nums[mid] < target) {
      left = mid + 1; // 白格：太小，永久扔掉 mid
    } else {
      right = mid; // 黑格：达标，保留 mid 继续往左找
    }
  }

  return left; // 撞头处 = 第一个 >= target 的位置 = 插入位置
};
```

这版为什么不会出 bug，对照新手三大坑：

| 新手坑               | 这版为什么免疫                                        |
| -------------------- | ----------------------------------------------------- |
| 死循环（`left=mid`） | `<` 走 `mid+1` 严格前进；`>=` 走 `right=mid` 严格缩小 |
| 越界偷看 mid±1       | 全程只碰 `nums[mid]`，没有邻居                        |
| 少 return / ±1       | 出口 `left===right` 就是答案，`return left` 一行收尾  |

## 四、35 母题：六个“为什么”逐个钉死

这道题是二分母题，把每个边界的为什么搞透，后面题就是换 `check`。

### ① 为什么 `right = nums.length`（不是 `length-1`）？

答案可能是插在末尾（target 比所有数都大），下标 = `length`。所以 right 要够得着 `length`。

### ② 为什么 `while (left < right)` 用 `<`（不是 `<=`）？

判据是：`while` 条件回答的是“区间里还有没有没检查的格子”。
左闭右开 `[left, right)` 里 right 那格不算数，是哨兵/终点线。当 `left === right` 时 `[left, left)` 是空区间，没东西可查了，该停，所以用 `<`。

对比精确查找用闭区间 `[left, right]`（两端都算数），`left===right` 时还剩一格要看，所以用 `<=`。两套各自自洽，别混用。

### ③ 为什么“小于走 left、大于等于走 right”？

```
if (nums[mid] < target)  left = mid + 1;   // 太小(白格) → left
else                     right = mid;       // 达标(黑格) → right
```

- `left` 管左端，负责往右推、扔掉左边。白格绝不是答案（答案是第一个黑格），往右扔。
- `right` 管右端，负责往左拉、缩小到左边。黑格可能是答案，往左缩着找更早的。

判据一句话：mid 有没有可能是答案？有可能就保留它（`right=mid`），绝无可能就扔掉它（`left=mid+1`）。

### ④ 为什么“相等”必须归 `>=` 这档（走 right），不能归 `<=`（走 left）？

`nums[mid] === target` 时 mid 正好站在答案上，是可能的答案，必须保留（走 `right=mid`）。

若把相等划给 left（写成 `<=`），会 `left=mid+1` 把正确答案直接扔到边界外：

```
nums=[1,3,5,6] 找 5：mid=2 nums[2]=5, 若 <= 走 left=3 → 答案5被扔掉 → 最终错误返回3（应为2）
```

相等就是达标、就是可能是答案，要保留，归 `>=` 走 right。达标的东西不能当“太小”扔掉。

### ⑤ 为什么 `left = mid + 1`（不是 `left = mid`）？防的是死循环

`mid = Math.floor(...)` 向下取整，当范围剩两个数时，`mid` 算出来永远等于 left：

```
left=0, right=1 → mid = floor(0.5) = 0 = left
```

- 若写 `left = mid`：等于 `left = left`，原地踏步，死循环。
- 写 `left = mid + 1`：`left` 严格前进至少 1 格，范围保证缩小，一定终止。

### ⑥ 为什么 `right = mid` 却不用 `-1`？这是不对称的根源

两点：

- 语义上，mid 是可能的答案要保留，`-1` 会把它弄丢；而 `left=mid+1` 走的是白格，确定不是答案要扔掉，所以 `+1`。
- 防死循环上，`mid = floor(...)` 时 mid 永远够不到 right（最大是 `right-1`），所以 `right = mid` 天然让 right 严格变小，不会原地踏步；而 mid 会等于 left，所以 `left=mid` 才危险、必须 `+1`。

口诀是闭端 ±1、开端不动：区间闭的那端收缩要 `±1`（那格算数、mid 又偏向它，得手动跨过防死循环）；区间开的那端不用 `±1`（那格本不算数、mid 又够不到它，直接顶上去就等于排除）。两端各看各的开闭。

## 六、二分的四种边界

35 这一问牵出了二分的全部对称结构：改“相等归哪档”就切换要找的目标。取整方向（floor/ceil）只是手段，真正决定找什么的是“相等归哪档 + return 谁”。

| 要找的目标                              | 相等时往哪走             | 收缩              | 返回           |
| --------------------------------------- | ------------------------ | ----------------- | -------------- |
| 第一个 `>= target`（35 / 34左边界）     | 往左（保留）`right=mid`  | `<`→`left=mid+1`  | `left`         |
| 第一个 `> target`（upper_bound）        | 往右（排除）`left=mid+1` | `<=`→`left=mid+1` | `left`         |
| 最后一个 `<= target`                    | 往右（保留）             | 见下方 ceil 版    | `left`/`right` |
| 最后一个 `< target`                     | 往左（排除）             | ...               | ...            |

实操上，找左边界/插入位置永远用 floor + lower_bound 这版。想切换目标，只改比较符（`<` / `<=`），别乱动模板结构。

### 关于向上取整的坑（真实踩坑记录）

一度想用 `Math.ceil` 镜像改写 35：ceil 偏右，配套 `right=mid-1`、`left=mid`、相等归 left（`<=`）。镜像直觉本身对（ceil 确实配 `right=mid-1`/`left=mid`），但把“相等归 left”一改，目标就从“第一个 ≥”翻转成“最后一个 ≤”，实跑 `[1,3,5,6]找2` 返回 0（应为1）。它答对了另一道题，不解 35。

教训是取整方向和“找什么”是两件独立的事，别一起改。35 找左边界就老老实实 floor + lower_bound，ceil 留给以后学“找右边界”再用。这也符合回溯笔记那条：验证靠运行，不靠脑补，这坑就是跑出来才发现的。

## 七、卸掉心智负担：6 个旋钮，其实只有 2 套合法组合

学到某个阶段一定会冒出这个焦虑：写二分是不是要同时想取整、想等号、想 +1、想返回谁，好多点？这一节专治这个。

### 二分确实有 6 个旋钮

```
① 取整      floor / ceil
② while     <  /  <=
③ left 收缩  = mid+1 / = mid
④ right 收缩 = mid-1 / = mid
⑤ 比较符    <  /  <=  /  >  /  >=
⑥ 返回      left / right / mid
```

如果每题都从零现调这 6 个，二分就是地狱，这也是它出名难写对的原因。

### 但 ①③④⑥ 会成套锁死，合法组合只有 2 套

关键在于这些旋钮不是独立的，必须配套，否则死循环。真正合法的组合只有两套：

A 套（floor + 左闭右开，找左边界），主力：

```javascript
right = nums.length;   while (left < right);   mid = floor(...)
nums[mid] <  target → left = mid + 1;   否则 right = mid;   return left;
```

B 套（ceil + 左开右闭，找右边界），备用：

```javascript
left = -1;             while (left < right);   mid = ceil(...)
nums[mid] >  target → right = mid - 1;   否则 left = mid;   return left;
```

③④ 由 ① 唯一决定，这是防死循环的硬约束，不是风格：

- 用 floor（mid 偏左、可能 `=left`）时，动 left 必须 `+1`（否则 `left=mid=left` 死循环）；动 right 不减（mid 够不到 right，`right=mid` 天然缩小）。锁死 A 套。
- 用 ceil（mid 偏右、可能 `=right`）时，动 right 必须 `-1`；动 left 不加。锁死 B 套。

所以你根本不用考虑 ③④，选了 floor（A 套），`left=mid+1`/`right=mid` 就自动定死，没有第二种合法写法，去纠结它只会纠结出死循环。

### 减负结论：背 1 套，临场只调 ⑤ 比较符

①②③④⑥ 像变速箱内部结构，出厂装配好，开车时不去拆。⑤ 比较符像方向盘，这才是每题真正要操作的。

背熟 A 套，把 ①②③④⑥ 当不可拆的封装整体记住，每题唯一要动脑的只有 ⑤：

- 找“第一个 `>= target`”，比较符写 `<`
- 找“第一个 `> target`”，比较符写 `<=`

这和回溯“一副骨架通吃、每题只填三要素”同源：骨架不重想，只填变化点。

## 八、因果链：取整决定 ±1，开闭决定语义

一个极易讲反的因果：`left=mid+1` 到底是因为“左闭右开”还是因为“floor”？是 floor，不是开闭。它俩在 A 套里恰好同向，容易混成一个。

拆成两个独立层次：

| 现象                      | 真正的原因                                   | 层次               |
| ------------------------- | -------------------------------------------- | ------------------ |
| `left = mid + 1`（要 +1） | floor 让 mid 可能 = left，不 +1 就死循环     | 防死循环（硬约束） |
| 扔掉 left 这格是合理的    | 左端闭、白格确定非答案                       | 语义（区间开闭）   |
| `right = mid`（不 -1）    | floor 让 mid 够不到 right，天然缩小           | 防死循环           |
| mid 顶上来即排除是合理的  | 右端开、那格本不算数                         | 语义               |

```
取整方向(floor/ceil) ──决定──► 收缩要不要 ±1（防死循环）
区间开闭(闭/开)       ──决定──► 收缩后那格算不算数（语义对不对）
```

在 A 套里两个原因碰巧同向（floor 要 +1，左闭也该扔，都指向 `left=mid+1`），所以才会误以为 +1 是因为左闭右开。记准：真正锁死 ±1 的是取整方向，不是开闭。这样推导任何变体都不翻车。

## 九、两个怕漏的追问（都验证过不漏）

### ⑴ `left` 总是 `+1`，会不会跳过答案？不会

`left = mid + 1` 只在 `nums[mid] < target` 这一个分支执行，也就是已经确定 mid 太小、100% 不是答案时才 +1。`+1` 跳过的永远是已验明正身的废格，一个真答案都不丢。

而可能是答案的格子（`nums[mid] >= target`）走的是 `right = mid`，`left` 纹丝不动，mid 稳稳留在范围里等着被 return。两条路各司其职：确定是废的就扔（+1），可能是宝的就留（`right=mid`，left 不动）。

已用 2 万组随机数据对拍暴力线性查找，结果 100% 一致，一个都没跳过。

### ⑵ 所以比较符只能写 `<`，不能写 `<=`（在找第一个 >= 时）

这是 ⑴ 的直接推论，可能是答案的不能跳过，就锁死了比较符：

```javascript
if (nums[mid] < target) left = mid + 1; // ✅ 只有严格太小才扔；等于时走 else 保留
if (nums[mid] <= target) left = mid + 1; // ❌ 把"正好=target"的答案也拖进 +1 跳过了！
```

`<=` 会在 `nums[mid] === target`（mid 正好是答案）时执行 `left=mid+1`，亲手把答案跳过去。

比较符的本质是控制“等于 target 的格子，留还是跳”：

- 找第一个 `>= target`（35/lower_bound），用 `<`，等于要留。
- 找第一个 `> target`（upper_bound），故意用 `<=`，因为就是要跳过所有 target，去找第一个严格大于的。

所以 `<=` 不是错，是换了个目标。这正是第七节“临场只调比较符”的微观机制。

## 十、实战三题：精确查找 / 复用 / 两段有序

### ⑴ LC74 搜索二维矩阵：把二维拉直成一维

题目特征：每行升序，且每行第一个数 > 上一行最后一个数，整个矩阵拉直就是一条完整升序数组。二维只是外表，本质是一维。假装它是长度 `m×n` 的一维数组做标准二分，取值时把一维下标翻译回二维坐标即可。

```javascript
const n = matrix[0].length; // 列数
const val = matrix[Math.floor(mid / n)][mid % n]; // 一维 mid → [行][列]
//                        ↑除法给行        ↑取余给列
```

两个踩过的坑：

- 行列都用列数 n 翻译，不是行数 m。因为每凑满 `n` 个元素才换一行，所以在第几行 = `⌊mid / n⌋`，`m` 在翻译里根本用不到。
- 74 是精确查找（问在不在，返回 true/false），用闭区间三档（`right = m*n-1`、`while <=`、`==` 即 `return true`、末尾 `return false`）。这是命中即返回的题，闭区间最顺手。

### ⑵ 三档 vs 两档：命中停不停决定档数

74 和 35 的写法差异，根子在命中 target 时要不要停：

| 场景                            | 命中 target 时 | 档数                     | 例题         |
| ------------------------------- | -------------- | ------------------------ | ------------ |
| 找在不在 / 找任意位置           | 立刻 `return`  | 3 档（`==`/`<`/`>`）     | 74、精确查找 |
| 找第一个 / 最后一个（边界）     | 不停，继续挤   | 2 档（`>=`/`<`）         | 35、34       |

三档的精确查找是二分最原始的样子；两档的找边界是把 `==` 并进 `>=` 的精简版，因为命中不能停，要找最左。

### ⑶ LC34 第一个和最后一个位置：一个 lower_bound 跑两次

核心不是写新二分，是复用 35 的 `find`（lower_bound），靠参数魔法变出各种查询：

```javascript
const start = find(target); // 第一个 >= target = 第一个 target
if (start === nums.length || nums[start] !== target) return [-1, -1]; // target 不存在
const end = find(target + 1) - 1; // (第一个 >= target+1) - 1 = 最后一个 target
```

参数魔法总表（`find(x)` = 第一个 ≥ x 的下标，永远只做这一件事）：

| 想要什么            | 怎么用 find          | 记忆                      |
| ------------------- | -------------------- | ------------------------- |
| 插入位置 / 第一个 = | `find(target)`       | find 直接给（这就是 35）  |
| 第一个 > target     | `find(target + 1)`   | "严格大于" = "≥ target+1" |
| 最后一个 = target   | `find(target+1) - 1` | 第一个 > 的前一格         |
| 最后一个 < target   | `find(target) - 1`   | 第一个 ≥ 的前一格         |

`find` 是一把尺子，把数组切成“< x ｜ ≥ x”一条缝，返回缝右边第一个。要右边第一个就直接读 `find`；要左边最后一个就 `find(...) - 1`（退一格）；要控制 x 本身归哪边，就喂 `target`（x 归右）还是 `target+1`（x 归左）。别背 4 条公式，记这一个动作，现场推。

别用“两端相等就停”的夹逼法（`while nums[left] != nums[right]`）：它命中 target 时指针不动会死循环；就算修好也会退化成 O(n)，因为它想验证整段都是 target（要两端同时到位），而二分只擅长逼近一条缝。正解是拆成两条缝，各跑一次 lower_bound。

### ⑷ LC33 搜索旋转排序数组：整体无序，但两段各自有序

旋转数组 `[4,5,6,7,0,1,2]` 不是乱，是两段升序加一个断崖。二分心法：

```
每一轮两层判断：
① 先看 mid 落在哪段（哪半是纯有序的）：nums[mid] >= nums[left] → 左段；否则右段
② 只在那段有序区间里判断 target 在不在 → 在就往那段走，else 排除法断定在另一半
```

```javascript
if (nums[mid] === target)
  return mid; // 精确查找，命中即返回
else if (nums[mid] >= nums[left]) {
  // ★ mid 在左段（>= 不能写 >，见下）
  if (nums[left] <= target && target < nums[mid])
    right = mid - 1; // target 在左段有序区
  else left = mid + 1; // 不在 → 排除法 → 去右半（else 不用再判断）
} else {
  // mid 在右段
  if (nums[mid] < target && target <= nums[right])
    left = mid + 1; // target 在右段有序区
  else right = mid - 1;
}
```

两个想通的点：

- 两层 if 不重复：第一层比 `nums[mid]` vs `nums[left]`（定位 mid 在哪段），第二层比 `target` vs 区间端点（定位 target）。一个定位 mid、一个定位 target，两码事。
- else 为什么不判断：左段有序、能一次判干净，“不在左段”经排除法等于“在右半”，无需再验；右半可能不有序，交给下一轮重新细分。每轮只精确处理有序的那半，也就是门卫心法：只在能确定的局部下规则。

跑 10 万组随机数据才测出来的坑：第一层 `nums[mid] >= nums[left]` 必须带等号。当 `mid === left`（范围剩一两个元素时），`nums[mid] === nums[left]`，写 `>` 会把它误判成右段，导致 `[16,2]`、`[7,1]` 这种全错。相等时 mid 就是左段第一个元素，要归左段，所以用 `>=`。

## 十一、最大痛点专治：`<` / `>` 到底加不加等号？

这是学二分最崩溃的点，等号有十几个位置，逐个记根本记不住。解药是不要记，要问。

万能口诀，每个 `<`/`>` 拿不准时问同一句话：相等的那一刻，我想让它走哪条路？

- 想走这条（这个值属于这边 / 我要包含它），加等号（`<=` / `>=`）
- 想走另一条（属于对面 / 我要排除它），不加（`<` / `>`）

所有等号问题归成 3 类：

| 类型                     | 判据                                                        | 例子（来自 33/35/74）                                                      |
| ------------------------ | ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| A. 端点值属于这一边      | 那个值是这段的成员，加等号                                  | `nums[left] <= target`、`target <= nums[right]`、`nums[mid] >= nums[left]` |
| B. 端点已被提前拦截      | 上面 `=== return` 过，相等不会发生，加不加都行，不加更清晰  | 33 里 `target < nums[mid]`（因为 `nums[mid]===target` 第一行已 return）    |
| C. 防死循环 / 防越界     | 由区间开闭 + floor 决定（见第八节）                         | `while (left < right)` vs `<=`                                             |

这跟门卫心法同源：回溯每个选择现场问“这条路能不能走”，二分每个等号现场问“相等走哪条路”。等号不是背下来的知识，是每次现场推出来的判断，记不住是正常的，因为它本就不该记。

## 十二、和回溯笔记的呼应

| 回溯里的心法                           | 二分里的对应                                       |
| -------------------------------------- | -------------------------------------------------- |
| 门卫心法：别判断局面，定规则让它自动拼 | 别偷看邻居抓现行，定收缩规则让 left 自动收敛到答案 |
| 分叉别用 else 二选一，两条都试         | 命中别急着 `return`，继续往左挤找更早的（见 §四④） |
| 验证靠运行不靠脑补                     | ceil 跑偏、死循环，都是跑出来才确认的              |
| 先写退出，再写循环                     | 先定找哪个边界（return 谁），再定收缩规则          |
