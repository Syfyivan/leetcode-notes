# GC与内存逃逸

## 核心回答（面试口述版，1 分钟能讲完）

Go 用并发三色标记清除，配合写屏障，STW 只在扫根和收尾两小段。对象不是栈上就是堆上：编译器做逃逸分析，引用可能活过当前函数就把对象放到堆。GC 触发看堆相对上次的增长率，默认 `GOGC=100`，堆大约翻倍就收一次；Go 1.19 起还有 `GOMEMLIMIT` 硬顶。返回局部变量指针在 Go 里安全，因为这个变量已经逃到堆上了。

## 展开

1. 三色标记 + 写屏障

   白：还没扫到。灰：自身已标，子指针还没扫完。黑：自己和子节点都标完。
   并发标记时用户代码还在改指针，需要写屏障维持不变量。Go 用混合写屏障（Dijkstra 插入 + Yuasa 删除）：赋值时把新白对象标灰，同时把被覆盖的旧指针也标灰。这样可以只在开始时 STW 扫一遍栈，结束再短 STW，不必第二次重新扫栈。标记完后清白色对象，有后台 sweeper。指针都在堆里对齐，非指针区域靠 bitmap 跳过。

2. 栈分配 vs 堆分配，逃逸分析

   栈上分配零开销，函数返回自动掉。堆上分配走 `mcache` → `mcentral` → `mheap`，还要被 GC 扫。
   常见逃逸：
   - 函数返回 `&x` 或包含 x 引用的对象
   - 赋给 `interface{}`（方法调用要盒子）
   - 发给未知函数、闭包把变量抓出去
   - 切片/对象太大，栈放不下
   - 被已经在堆上的对象引用

   `go build -gcflags="-m"` 会打印 `moved to heap`。

3. GC 触发时机与调优（GOGC）

   目标堆 = 存活堆 * (1 + GOGC/100)。GOGC=100 表示活着 100MB 就允许再长 100MB。GOGC=off 关掉自动 GC。`GOMEMLIMIT` 把总内存（含栈、堆外）卡住，接近上限时更积极地收。pprof 的 `heap`、`allocs`，以及 `runtime.ReadMemStats` 的 `PauseTotalNs`、`NumGC` 是观察口。降延迟优先看逃逸和短命大对象，别一上来把 GOGC 拧到 200 掩盖分配。

## 延伸

- 相关题：slice 与 map 底层。小切片长期引用大数组，逃逸分析救不了，要 `copy`。
- 对比：GOGC 调大少跑 GC，内存会涨。`GOMEMLIMIT` 是硬顶，靠近上限时收得更勤。
- 加码：热路径上看 `allocs/op` 和 `-gcflags=-m`，把 `interface{}` 装箱干掉。Go 1.18 用类型参数。

## 代码 / 例子

```go
func stackOK() int {
    x := 1
    return x // x 在栈上
}

func escape() *int {
    x := 1
    return &x // x escaped to heap
}

func box() interface{} {
    x := 1
    return x // 装箱，逃逸
}
```

## 常见追问

- Q: 怎么判断一个变量会不会逃逸到堆？
  A: 先想生命周期：有没有引用流出当前函数。不确定就 `go build -gcflags="-m -l"`（`-l` 关内联，打印更全）。也可以看编译器 SSA：`go build -gcflags="-m=2"`。benchmark 前后对比 `allocs/op`。面试口述举两例就够：返回指针必逃逸；只在函数内用的小变量通常不逃。
- Q: 返回局部变量指针在 Go 里为什么安全？
  A: C 里返回局部地址是悬垂指针，栈帧销毁就没了。Go 编译器发现 `&x` 流出，把 x 改到堆上分配，指针一直有效，直到没人引用被 GC 收走。安全的代价是一次堆分配和后续扫描。能返回值就返回值，别习惯性返回指针。

## 自己的易错点 / 之前答崩过的地方

- 把对象塞进 `interface{}` 再断言回来，只是为了泛型，额外制造逃逸。Go 1.18 用类型参数。
- `defer` 里用闭包抓大 slice，把本该随函数死掉的缓冲活到函数结束（通常还好），若再赋给全局就真逃了。
- 以为 STW 等于「GC 全程停世界」。现在停的是微秒到毫秒级的两段，标记和清除与用户代码并发。
- `sync.Pool` 取出来当长缓存用。Pool 在每次 GC 会掉一部分，当缓存会突然变慢。
