# 接口与鸭子类型

## 核心回答（面试口述版，1 分钟能讲完）

Go 的接口是隐式满足：类型不用写 `implements`，方法集对上就算实现。空接口 `interface{}`（Go 1.18 起别名 `any`）可以装任何值。接口值在运行时是「类型 + 数据」两份指针：非空接口是 `iface{tab, data}`，空接口是 `eface{_type, data}`。最常见的坑是 typed nil：`var p *T = nil; var i error = p`，这时 `i != nil`，因为 tab 不是空的。

## 展开

1. 接口的隐式实现

   `type Reader interface { Read(p []byte) (int, error) }`。`*os.File` 有这个方法就满足 `io.Reader`，不用登记。好处是标准库能定义 `io.Reader`，用户类型事后就能塞进去。方法集规则：值接收者，T 和 *T 都满足；指针接收者，只有 *T 满足。因为调指针方法要能取址。

2. 空接口 interface{} 与类型断言

   空接口没有方法，任何类型都满足。取出时用断言 `v, ok := i.(string)`，或 type switch。断言失败且不用 `ok` 会 panic。`any` 只是别名，没有新语义。泛型出来之后很多 `interface{}` 容器可以换成 `T`。

3. 接口的底层结构（type + value）

   非空接口 `iface`：`tab` 指向 `itable`（接口方法到具体类型方法的跳表）+ `data` 指向实际值。空接口 `eface`：`_type` + `data`。把值赋给接口，若超过一个机器字或调用方需要取址，会发生逃逸，值被拷到堆上再让 data 指向它。比较 `==` 时先比类型再比值；两边都是 nil 接口才相等。

## 代码 / 例子

```go
type closer interface{ Close() error }

type file struct{}
func (f *file) Close() error { return nil }

func wrap() closer {
    var f *file = nil
    return f // 返回的接口：tab=*file，data=nil
}

func main() {
    var c closer = wrap()
    fmt.Println(c == nil) // false
    if c != nil {
        _ = c.Close() // 能调到方法，receiver 是 nil 指针
    }
}
```

## 常见追问

- Q: 接口值为 nil 但类型不为 nil 的坑（nil != nil）？
  A: 接口的 nil 判断是 tab 和 data 都空。`var err error = (*os.PathError)(nil)` 的 tab 已经是 PathError 的 itable，所以 `err != nil`。函数里 `var e *MyError; return e` 会踩这个坑。正确是 `return nil`，让编译器构造真的空接口。`fmt.Printf("%#v", err)` 能看出类型。
- Q: 值接收者和指针接收者对接口实现的影响？
  A: 方法是值接收者，`T` 和 `*T` 都能赋给接口。方法是指针接收者，只有 `*T` 能赋；`T` 赋会编译失败，因为接口里的 data 可能不可取址（来自 map 元素、短生命临时值）。需要改接收者状态时用指针接收者，纯查询用值接收者。混用会让方法集对不上。

## 自己的易错点 / 之前答崩过的地方

- `error` 返回 typed nil，调用方 `if err != nil` 永远走进去，日志还是 `<nil>`。
- 给接口里的值调指针方法：编译过了，运行时 data 是拷贝，改了也不回写。小对象赋接口常拷贝。
- 用空接口装 slice 再断言成 `[]any`，`[]int` 断言不到 `[]any`，要自己循环装。
- 以为实现接口要在类型旁边写注释 `implements`。那只是给人看的，编译器不看。
