# 主从复制与读写分离

## 核心回答（面试口述版，1 分钟能讲完）

InnoDB 主库把变更写 binlog，从库 IO 线程拉过来写成 relay log，SQL 线程（或 8.0 的 worker 并行）重放。binlog 三种格式：STATEMENT、ROW、MIXED，现在默认 ROW，避免不确定函数在两边跑出不同结果。读写分离把 SELECT 丢从库，写走主库。代价是复制延迟：刚写入从库还没有。半同步让至少一台从库收到日志主库才返回，降低丢数据窗口，不消灭延迟。

## 展开

1. binlog 复制原理（三种格式）

   - **STATEMENT**：记 SQL。省空间，但 `NOW()`、`UUID()`、`LIMIT` 无 ORDER 会不一致。
   - **ROW**：记每行改前改后。安全，磁盘和网络更重。`binlog_row_image=FULL/MINIMAL`。
   - **MIXED**：能安全用语句就语句，否则 ROW。

   链路：主库 dump 线程 → 从库 IO 线程写 `relay-bin` → SQL 线程回放。5.7+ GTID 让位点变成 `uuid:seq`，failover 少算坐标。并行复制按 schema 或 write set（`slave_parallel_type=LOGICAL_CLOCK`）。

2. 主从延迟的原因与应对

   大事务（从库要一次性重放）、从库单线程 SQL、从库机器更弱、DDL、表没主键导致 ROW 全表扫、网络。应对：小事务、给表加主键、并行复制、从库只读并加足够 innodb 缓冲、把报表拆到历史库。监控 `Seconds_Behind_Master` 不准时看 `performance_schema.replication_applier_status_by_worker`。

3. 读写分离后读到旧数据怎么办

   这是「读己之写」问题。策略：
   - 写后一段时间内强制读主
   - 中间件按 GTID / binlog 位点等从库追上再读（`WAIT_UNTIL_SQL_THREAD_AFTER_GTIDS`）
   - 会话粘滞：同一用户写过就绑主
   - 业务接受最终一致的读走从，余额、库存确认走主

## 延伸

- 相关题：事务与 ACID。binlog 和 redo 的内部 XA，保证崩溃恢复和主从对得上。
- 对比：STATEMENT 省空间但不安全，ROW 现在默认。没主键的表 ROW 回放会扫全表，延迟爆炸。
- 加码：GTID failover 少算坐标。并行复制看 write set，大事务照样把从库拖住。

## 代码 / 例子

```sql
-- 主
SHOW MASTER STATUS;          -- File, Position, 或 GTID
-- 从
SHOW SLAVE STATUS\G          -- Seconds_Behind_Master, Last_Errno
-- 8.0
SHOW REPLICA STATUS\G

-- 等从库追到
SELECT WAIT_UNTIL_SQL_THREAD_AFTER_GTIDS('uuid:100', 3);
```

## 常见追问

- Q: 主从延迟下刚写完就读，读不到怎么解决？
  A: 对一致性敏感的读指定主库；或应用记下这次写入的 GTID，读从库前 `WAIT ... AFTER_GTIDS`，超时则回主库。缓存也可以：写库同时写 Redis，读先走缓存。不要靠「sleep 200ms」，延迟会抖。
- Q: 半同步复制解决了什么？
  A: 异步模式下主库写完 binlog 就提交返回，主库一挂，从库可能还没收到最后几条，failover 丢数。半同步（after_sync）：至少 N 个从库 ACK 收到日志，主库才提交返回。解决的是「主挂丢数据」，不解决「从库应用慢导致读旧」。从库全挂会退化成异步，要配超时。

## 自己的易错点 / 之前答崩过的地方

- 把半同步说成同步：从库执行完才返回。半同步 ACK 的是收到日志，不是 SQL 线程跑完。
- 从库当主用却开了只读以外的写入，数据分叉。
- 表没有主键，ROW 模式下从库用二级索引甚至全表定位行，延迟爆炸。
