# 锁机制

## 核心回答（面试口述版，1 分钟能讲完）

InnoDB 默认行锁，锁在索引项上。共享锁 S 给读（`SELECT ... LOCK IN SHARE MODE` / `FOR SHARE`），排他锁 X 给写（`FOR UPDATE` / `UPDATE` / `DELETE`）。范围上还有间隙锁 Gap，临键锁 Next-Key = 记录锁 + 左边间隙，RR 用它防幻读。表级意向锁 IS / IX 是个快速路标：要加表 X 锁时看有没有行锁，不必扫所有行。`UPDATE` 没走索引会扫描全表，每一行都加 X 锁，效果接近锁表。

## 展开

1. 行锁/表锁/间隙锁/临键锁

   - **记录锁 Record**：锁住索引上已有的行。
   - **间隙锁 Gap**：锁住索引记录之间的空洞，例如 `(10, 20)`，阻止插入 15。
   - **临键锁 Next-Key**：Record + 左开右闭间隙，RR 当前读的默认形态。
   - **插入意向锁**：插入前在间隙上放的一种 Gap，和普通 Gap 冲突，插入之间不互相堵。
   - **表锁**：`LOCK TABLES`，或没有索引时退化成「锁很多行」。DDL 还有 metadata lock。

2. 共享锁 S 与排他锁 X

   S 与 S 兼容，S 与 X、X 与 X 不兼容。当前读才加这些锁，普通 SELECT 在 RC/RR 下是快照读，不加 S。`UPDATE` 先在二级索引上锁，再回表锁主键，顺序反了容易和别的语句死锁。

3. 意向锁的作用

   IS：事务想在某行加 S；IX：想在某行加 X。意向锁之间兼容，和表级 S/X 冲突。目的：事务要 `LOCK TABLE t READ` 时，看表上有没有 IX，有就等，不用去行上逐个问。意向锁是表级的，自动加。

## 代码 / 例子

```sql
-- RR 下当前读：id=10 的记录锁 + 间隙
SELECT * FROM t WHERE id = 10 FOR UPDATE;

-- 没走索引：type=ALL，扫描到的行全部 X 锁
UPDATE t SET s = 1 WHERE name = 'alice'; -- name 无索引

-- 看锁（8.0）
SELECT ENGINE_TRANSACTION_ID, INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks;
```

## 常见追问

- Q: 为什么 UPDATE 没走索引会锁全表？
  A: 行锁挂在索引记录上。没有合适索引就沿着主键聚簇索引逐行判断 WHERE，扫描过的行都要加 X 锁（RR 下连间隙也锁）。即使最终只改 1 行，也可能把整棵树锁住。加索引让优化器走 range/ref，只锁命中的记录和必要间隙。
- Q: 死锁是怎么产生的，怎么排查？
  A: 两个事务各持一把锁，再要对方的锁，成环。典型：T1 改 A 再改 B，T2 改 B 再改 A。InnoDB 有死锁检测，挑 undo 少的回滚，错误 `1213 Deadlock found`。排查：`SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK，或 8.0 的 `data_locks` / `data_lock_waits`。预防：固定加锁顺序、索引减少扫描范围、缩短事务、`innodb_deadlock_detect` 极大并发时可改成等超时（一般不关检测）。

## 自己的易错点 / 之前答崩过的地方

- 说「InnoDB 只有行锁」。表级意向锁、MDL、自增锁、Gap 都在。
- 把 Gap 锁理解成锁一行。它锁的是空隙，空表上 `WHERE id > 1 FOR UPDATE` 也能挡住所有插入。
- 以为 `SELECT` 都会加锁。默认隔离级别下普通 SELECT 不加行锁。
- RC 和 RR 的锁范围不同，拿 RC 的现象去答 RR 的题。
