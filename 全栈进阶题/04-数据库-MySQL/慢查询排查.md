# 慢查询排查

## 核心回答（面试口述版，1 分钟能讲完）

线上慢查询三步：先确认是哪条 SQL、跑了多久、扫了多少行；再 `EXPLAIN` / `EXPLAIN ANALYZE` 看访问类型和 Extra；最后决定加索引、改写法、还是改架构。入口是慢查询日志（`slow_query_log`、`long_query_time`）和 `performance_schema`。加了索引还慢，常见原因是没真正用上、回表太多、排序临时表、锁等待、缓冲池没命中、或者 SQL 根本该走缓存 / ES。

## 展开

1. 慢查询日志开启与定位

   ```sql
   SET GLOBAL slow_query_log = ON;
   SET GLOBAL long_query_time = 0.2;          -- 秒
   SET GLOBAL log_queries_not_using_indexes = ON;
   ```

   日志在 `slow_query_log_file`。用 `mysqldumpslow` 或 `pt-query-digest` 按次数、总耗时聚合。8.0 也可以从 `performance_schema.events_statements_summary_by_digest` 看 `SUM_TIMER_WAIT`、`COUNT_STAR`。先抓「总耗时最高」而不是单次最慢的那条。

2. 从 EXPLAIN 到加索引/改 SQL 的流程

   - `type=ALL` 且 `rows` 很大：加索引或改条件让它能 range/ref。
   - `Using filesort`：让 ORDER BY 和 WHERE 用同一联合索引。
   - `Using temporary`：GROUP BY 字段补进索引，或先过滤再聚合。
   - 回表严重：覆盖索引，或拆成延迟 JOIN。
   - 深分页：seek 法。
   改完在从库或备份上 `EXPLAIN ANALYZE`，看 `actual time` 和 `rows`。别在主库对大表 `ALTER` 不加 online DDL 策略。

3. profiling 看各阶段耗时

   旧的 `SHOW PROFILE` 已不推荐。用 `performance_schema` 的 `events_stages_*`，或 `EXPLAIN ANALYZE` 的 Iterator 树。还要分清：SQL 执行慢，还是等锁（`sys.innodb_lock_waits`）、等 IO（`Handler_read_*`、`Innodb_buffer_pool_reads`）、等网络。`SHOW PROCESSLIST` / `performance_schema.threads` 看 `State`：`Sending data`、`Locked`、`Waiting for ... lock`。

## 延伸

- 相关题：锁机制。PROCESSLIST 的 State 是 `Locked`，先查行锁等待，别急着加索引。
- 对比：实验室 `EXPLAIN` 和线上缓冲池命中是两回事。冷数据全是随机 IO。
- 加码：大表 DDL 用 8.0 inplace / pt-osc / gh-ost。主库直接 `ALTER` 会把写堵住。

## 代码 / 例子

```sql
-- 8.0 看真实计划
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42 ORDER BY id DESC LIMIT 20;

-- 最近的昂贵语句
SELECT DIGEST_TEXT, COUNT_STAR, AVG_TIMER_WAIT/1e12 AS avg_s
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;
```

## 常见追问

- Q: 一条线上慢 SQL，你的排查步骤是什么？
  A: 1) 慢日志或 APM 拿到完整 SQL 和绑定参数。2) `SHOW PROCESSLIST` 看是否在等锁、是否在扫表。3) 同等数据量上 `EXPLAIN ANALYZE`。4) 对照表结构和已有索引，决定加联合索引还是改 WHERE。5) 看扫描行 * 回表是否把缓冲池打爆，必要时覆盖索引。6) 上线用 pt-osc / 8.0 instant/inplace DDL。7) 观察 QPS、P99、是否引入更重的写。
- Q: 加了索引还是慢，可能是什么原因？
  A: 优化器没用它（选择率差、统计信息过期 `ANALYZE TABLE`）；隐式转换 / 函数导致失效；`SELECT *` 回表随机 IO；排序和分组仍 filesort；结果集太大网络发送慢；InnoDB 行锁等；索引本身太大，热数据不在 buffer pool；OR / UNION 把计划拆烂。还有一种：SQL 不慢，慢在应用 N+1。

## 自己的易错点 / 之前答崩过的地方

- 只看单次 5 秒的 SQL，忽略每秒跑 1000 次、每次 20ms 的那条，20ms 那条总 CPU 更高。
- 在主库直接 `ALTER TABLE ADD INDEX` 锁表。大表要用 online DDL 或 gh-ost。
- 把 `long_query_time=10` 当默认还觉得没慢查询，P99 已经 800ms 了。
