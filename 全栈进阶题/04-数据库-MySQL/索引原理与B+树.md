# 索引原理与B+树

## 核心回答（面试口述版，1 分钟能讲完）

InnoDB 的索引是 B+ 树。真正的行数据在主键这棵树的叶子上，这叫聚簇索引。二级索引叶子只存「索引键 + 主键值」，不够的列要拿主键再回表。选 B+ 是因为叶子串成双向链表，范围查询顺序扫盘；内部节点不放行数据，同样大小的页能放下更多扇出，树更矮，IO 更少。联合索引遵循最左前缀：`(a,b,c)` 能走 `a`、`a,b`、`a,b,c`，单独 `b` 用不上。

## 展开

1. 为什么用 B+ 树而不是 B 树 / 红黑树 / 哈希

   - **哈希**：`O(1)` 等值，不能范围、不能排序。InnoDB 有自适应哈希，是 B+ 树上热点的额外缓存，不是主键结构。
   - **红黑树 / 二叉**：高度 `log2(n)`，一千万行约 24 层，每次一层一次随机 IO，磁盘受不了。
   - **B 树**：内部节点也放数据，扇出变小，树更高；范围查询要中序来回跳。
   - **B+ 树**：内部节点只放键和页指针，一页 16KB 能放上千个指针，三层就能覆盖千万到亿级。叶子存行（或主键），并且用指针串起来，`BETWEEN`、`ORDER BY` 沿链表走。

2. 聚簇索引 vs 二级索引、回表

   聚簇索引 = 主键 B+ 树，叶子是完整行。没有主键时 InnoDB 挑非空唯一键，再没有就造 6 字节 `row_id`。
   二级索引叶子：`(二级键, 主键)`。查 `WHERE name='a'` 先在 name 树上定位主键，再去主键树拿整行，这就是回表，两次 IO 路径。
   主键尽量短、稳定：二级索引每个条目都带一份主键。

3. 联合索引与最左前缀

   `(a,b,c)` 按 a，a 相同再 b，再 c 排序。`WHERE a=1 AND b=2` 能走；`WHERE b=2` 走不了（除非 index skip scan，8.0 优化器偶尔用，别指望）。`LIKE 'ab%'` 能走，`LIKE '%ab'` 不能。`ORDER BY b` 在 `a=?` 已经等值时可以用到索引顺序，避免 filesort。

## 延伸

- 相关题：锁机制。行锁挂在索引记录上，没索引就锁很多行。和「UPDATE 没走索引会锁全表」是同一件事。
- 对比：主键短且趋势递增，二级索引每条都带着主键。UUID 当主键会把所有二级索引撑肥。
- 加码：联合索引 `(a,b,c)` 对 `ORDER BY c`，在 a、b 等值时能用上有序性，少一次 filesort。

## 代码 / 例子

```sql
CREATE TABLE t (
  id BIGINT PRIMARY KEY AUTO_INCREMENT, -- 聚簇索引
  uid BIGINT NOT NULL,
  status TINYINT,
  KEY idx_uid_status (uid, status)      -- 二级联合索引
);

-- 覆盖索引：叶子已有 uid,status,id，不必回表
SELECT status FROM t WHERE uid = 42;

-- 最左前缀：用上 uid，status 做过滤
SELECT * FROM t WHERE uid = 42 AND status = 1;
```

## 常见追问

- Q: 为什么建议用自增主键？
  A: 插入总是追加到叶子最右，页分裂少，B+ 树更紧。随机 UUID 当主键会在中间页插入，页分裂、碎片、缓冲池命中率掉。二级索引还要复制主键，UUID 16 字节比 BIGINT 8 字节更肥。业务需要全局唯一且趋势递增，用雪花 ID，别用无序 UUID。
- Q: 覆盖索引是什么，怎么避免回表？
  A: 查询需要的列全在某一个索引叶子上，Extra 显示 `Using index`。联合索引把高频查询列带上，或用 `INCLUDE` 思想把覆盖列放进联合索引尾部。`SELECT *` 很难覆盖。主键查询本身就在聚簇索引上，没有回表。

## 自己的易错点 / 之前答崩过的地方

- 把「聚簇」说成「有索引」。MyISAM 主键也是二级结构，行在堆里，InnoDB 才把行塞进主键叶子。
- 以为联合索引 ` (a,b) ` 对 `WHERE b=?` 一定失效。8.0 可能 skip scan，但代价高，该单独建 `b` 还是要建。
- 索引越多越好。每个二级索引都要维护，写放大，缓冲池被索引页挤掉。
