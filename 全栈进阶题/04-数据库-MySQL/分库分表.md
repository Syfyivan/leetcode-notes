# 分库分表

## 核心回答（面试口述版，1 分钟能讲完）

单表太大或单机写满时才拆。垂直拆：按业务把表放到不同库（用户库、订单库），减少单机表数量和无关列。水平拆：同一张表按分片键拆成多表或多库，例如 `order_id % 16` 或按用户 ID 哈希。分片键要出现在几乎所有查询里，不然就要扫所有片。拆完跨库 JOIN、分布式事务、全局有序分页、全局 ID 都会变难，所以先垂直、先归档、先读写分离，真顶不住再水平。

## 展开

1. 垂直拆分 vs 水平拆分

   垂直：`user` 和 `order` 不同库；或把大字段（简介、正文）拆冷表。好处是边界清晰，事务大多还在一库内。
   水平：`order_0` ... `order_15`，结构相同。按范围（时间、ID 段）或哈希。范围好扩容、易热点；哈希均匀、扩容要迁移。

2. 分片键选择、路由

   选「查询和写入都带上的列」。订单系统常用 `user_id`，因为用户维度查询最多。用 `order_id` 哈希则按用户查要二级索引或映射表。路由在应用、中间件（ShardingSphere、Vitess）或代理完成。绑定表（字典表）可复制到每片避免跨库 JOIN。

3. 带来的问题（跨库 join、分布式事务、全局 ID）

   - JOIN：应用侧拼，或冗余字段，或限制「只允许同 user_id 的 JOIN」。
   - 事务：尽量单片事务。跨片用本地消息表 + 出箱，或 TCC，别默认 XA。
   - ID：自增主键各片会撞，改用号段或雪花。
   - 扩容：哈希取模扩一倍要翻倍迁移，一致性哈希能少搬。
   - 运维：DDL 要在每片上跑，监控和备份翻倍。

## 延伸

- 相关题：分布式 ID。拆之前先把主键策略换掉，自增各片会撞。
- 对比：哈希均匀但扩容要搬家；按时间范围好扩，容易热点。
- 加码：双写 + 校验是迁移常用手段。一次切哈希取模，对不上就回不去。跨片 UNIQUE 只在一片内有效。

## 代码 / 例子

```sql
-- 路由伪代码：片 = user_id % 16
SELECT * FROM order_07 WHERE user_id = 23 AND id = 1001;

-- 全局分页（不准）：各片 LIMIT 20 再在内存排，只适第一页
-- 更好：WHERE user_id=? AND id < last_id ORDER BY id DESC LIMIT 20
```

## 常见追问

- Q: 分表后怎么做分页查询？
  A: 带分片键的分页和单表一样，seek 法 `id < last`。不带分片键的全局分页最痛：每片取一页在内存归并，深页代价是片数 × offset。做法：禁止深页；按时间范围先定片；用 ES / 宽表做查询侧；业务改成「加载更多」而不是跳页。
- Q: 什么时候才真的需要分库分表？
  A: 单表行数到千万～亿、索引和数据盘放不下、写 QPS 把单机 redo / 锁打满，而且归档、升级硬件、读写分离、分区表都试过了。提前按 user_id 预留分片字段可以，但过早上中间件会把开发效率吃掉。能用分区表（PARTITION BY RANGE）解决冷热的，先别拆库。

## 自己的易错点 / 之前答崩过的地方

- 用 `create_time` 当唯一分片键，用户查自己的订单要扫所有时间片。
- 水平拆完还在用跨片 UNIQUE，唯一约束只在一片内有效，手机号全局唯一要单独索引表。
- 把分库分表当缓存的替代。两者解决的问题不同，缓存抗读，分片抗数据和写。
