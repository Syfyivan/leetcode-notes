# 幂等性设计

## 核心回答（面试口述版，1 分钟能讲完）

幂等：同一个请求打一次和打 N 次，对系统的效果一样。HTTP 里 GET、PUT、DELETE、HEAD 按语义幂等，POST 不幂等。支付、下单、扣库存这些 POST 必须自己做：数据库唯一索引、去重表、状态机、或前端申请的幂等 token。网络重试、消息队列至少一次投递、用户连点，都会把同一笔业务送进来第二次。

## 展开

1. 幂等的定义、哪些操作天然幂等

   「效果一样」不是「响应字节一模一样」。第一次创建返回 201，第二次返回 200 和同一资源，仍算幂等。天然幂等：把字段设成某个值、按主键删除、查询。不幂等：插入新行、余额 += 金额、发券。

2. 唯一索引/token 令牌/状态机/去重表

   - **唯一索引**：订单号、`user_id + sku + 活动日` 唯一，第二次插入 1062，当成成功返回原单。
   - **token**：开始时服务端发一次性 token，提交带着它，Redis `SET token used NX EX 86400`，种不上就拒绝或返回上次结果。
   - **状态机**：订单 `created → paid → shipped`，已是 paid 再收支付成功事件直接 ack。
   - **去重表**：`(scope, idemp_key)` 主键，事务里先插去重行再做事，插失败则读原结果。

3. 接口重试与幂等的关系

   客户端超时不知道服务器有没有做成，只能重试。所以超时重试要求服务端幂等。MQ 消费者同理：at-least-once 必须消费幂等。重试要有上限和退避，幂等键要贯穿：HTTP `Idempotency-Key`、消息 `messageId`。

## 代码 / 例子

```sql
CREATE TABLE uniq_order (
  request_id CHAR(36) PRIMARY KEY,
  order_id   BIGINT NOT NULL
);

START TRANSACTION;
INSERT INTO uniq_order(request_id, order_id) VALUES (?, ?);
INSERT INTO orders(...) VALUES (...);
COMMIT;
-- 第二次：主键冲突，SELECT order_id FROM uniq_order WHERE request_id=?
```

## 常见追问

- Q: 支付/下单接口怎么保证幂等？
  A: 客户端生成 `request_id`（或用支付渠道流水号）。服务端以它做唯一键：事务内插去重表 + 插订单。冲突则返回已有订单，不扣第二次库存。库存本身用乐观版本或 `UPDATE stock SET n=n-1 WHERE n>=1`。钱相关再加状态机，`paid` 状态重复通知只记日志。渠道回调也用流水号去重。
- Q: 前端重复点击提交，后端怎么兜底？
  A: 前端按钮 disable 只是体验，网络重试仍会来。后端必须认幂等键。没有键时退而求其次：短时间窗口 Redis `SET user:9:create-order 1 NX EX 5` 防连点，但挡不住 6 秒后的重试，正式下单还是要业务唯一键。

## 自己的易错点 / 之前答崩过的地方

- 只在 Nginx 层按 URL 去重，body 不同的合法第二次下单被挡。
- 去重表和订单表不在同一事务，先插订单后插去重失败，重试又插一单。
- 把「返回相同 JSON」当成幂等，内部却扣了两次库存。
