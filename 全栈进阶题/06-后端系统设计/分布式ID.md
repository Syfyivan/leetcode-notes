# 分布式ID

## 核心回答（面试口述版，1 分钟能讲完）

分库分表后不能靠单机 `AUTO_INCREMENT` 当全局主键。常见方案：UUID、DB 号段、Redis INCR、雪花算法。业务表主键要趋势递增，InnoDB 聚簇索引才不会随机页分裂，所以 UUID 版本 4 不适合当主键。雪花是 64 位：1 位符号 + 41 位毫秒时间 + 10 位机器 + 12 位序列，单机每毫秒 4096 个。它依赖时钟，时钟回拨会撞号，要挡住或换方案。

## 展开

1. UUID/数据库自增/号段/雪花算法对比

   | 方案 | 递增 | 性能 | 依赖 | 问题 |
   | --- | --- | --- | --- | --- |
   | UUID v4 | 否 | 本地快 | 无 | 16 字节，索引碎 |
   | DB 自增 | 是 | 受 DB | 单库 | 难水平扩 |
   | 号段（美团 Leaf） | 趋势增 | 高 | DB | 号段丢失造成空洞 |
   | Redis INCR | 是 | 高 | Redis | Redis 挂了要切 |
   | 雪花 | 趋势增 | 本地最快 | 时钟+机器号 | 回拨、机器号分配 |

   号段：DB 里一行 `max_id`，每次取 1000 个，应用内存里发，发完再要。

2. 雪花算法的位分配、时钟回拨问题

   默认 41 位时间从自定义 epoch 起，能用 69 年。10 位 worker 可 1024 台，也可拆成机房 + 机器。12 位序列同一毫秒内递增，溢出则等到下一毫秒。
   时钟回拨：若回拨很小，等待追上；若回拨大，拒绝发号或借用未来位。worker id 冲突（两台容器拿到同一个）会双机同号。K8s 里用稳定的 StatefulSet 序号或 ZooKeeper 租约。

3. 趋势递增对数据库索引的意义

   InnoDB 按主键顺序插叶子页。趋势递增 ≈ 追加写，页填充满再分裂，缓冲池友好。随机 UUID 在树中间插，页频繁分裂，二级索引更肥。有序到单点也有热页争用，高写入可把雪花的时间差打散一点，或用号段。UUIDv7 / ULID 也是时间有序，比 v4 适合当主键，仍比 BIGINT 宽。

## 延伸

- 相关题：索引原理与 B+ 树。随机主键页分裂，和「为什么自增主键」是一道题。
- 对比：号段依赖 DB 但好懂；雪花本地最快，绑时钟和机器号。Redis INCR 没持久化，重启会从 1 再数。
- 加码：雪花 ID 给前端要用字符串，JS `Number` 超过 `2^53-1` 会丢精度。K8s 里 workerId 用 StatefulSet 序号或 etcd 租约。

## 代码 / 例子

```text
# 64-bit 雪花
# 0 | 41bit timestamp | 10bit worker | 12bit seq
id = ((now - epoch) << 22) | (worker << 12) | seq

# 号段
UPDATE leaf SET max_id = max_id + 1000 WHERE tag='order';
# 应用发放 (old, new]
```

## 常见追问

- Q: 雪花算法时钟回拨了怎么办？
  A: 回拨小于某个阈值就 sleep 等到单调；超过阈值直接报错，让调用方换实例。记录 lastTimestamp，发现 now < last 就是回拨。容器迁移后 NTP 校准也可能跳。生产常加「序列用完等到下一毫秒」和监控 `clock_backward`。不想处理时钟就用号段，ID 在 DB 里发。
- Q: 为什么不直接用 UUID 做主键？
  A: v4 随机，聚簇索引随机插入，页分裂、碎片、二级索引每条多 8 字节以上。字符串 UUID 比较也慢。若必须全球唯一且离线生成，用 UUIDv7 或把雪花当 `BIGINT`。对外暴露可以再套一层编码，内部主键仍用长整型。

## 自己的易错点 / 之前答崩过的地方

- 雪花 ID 丢给前端，JS `Number` 超过 2^53-1 精度丢了，要用字符串传。
- workerId 写死成 1，水平扩两个实例就开始撞主键。
- 用 Redis INCR 当唯一来源却没持久化，重启从 1 再数。
