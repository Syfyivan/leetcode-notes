# 消息队列与削峰

## 核心回答（面试口述版，1 分钟能讲完）

MQ 三件事：解耦（下单和发积分不互相 import）、异步（HTTP 先返回，邮件后发）、削峰（秒杀请求进队列，消费者按库存速度消化）。代价是延迟、运维、以及三个经典问题：消息丢、重复消费、要保序。投递语义里 at-least-once 最常见，用生产者确认 + 持久化 + 消费 ACK 防丢，用幂等防重复。积压了就扩消费者、临时跳过非关键、或者上死信。

## 展开

1. MQ 的三大作用（解耦/异步/削峰）

   解耦：发布者只认识 topic，不认识下游几个系统。
   异步：慢 IO 从请求线程拿掉，接口 P99 下来。
   削峰：入口瞬时 10 万 QPS，消费者 2 千，队列顶住，DB 不被打死。队列有长度上限，满了要拒流或降级。

2. 消息丢失、重复消费、顺序消费

   丢：生产者没确认就认为成功；broker 没落盘就挂；消费者没处理完就 ACK。
   重复：生产者重试、broker 重投、消费者超时再投，at-least-once 的必然产物。
   顺序：单分区 / 单队列 + 同一业务键哈希到同一分区，消费者单线程处理该分区。多分区全局无序。Kafka 是分区有序，RabbitMQ 单队列有序但并行消费会乱。

3. 消费幂等、死信队列

   消费侧用消息 id 去重表，或依赖业务状态机。失败重试几次进 DLQ，人工或专门消费者修。不要无限重试把分区卡住。削峰场景：入口校验 + 令牌，过了的才进 MQ，库存用预扣，消费者做最终扣减。

## 延伸

- 相关题：限流算法。削峰是进队，限流是拒在门外。秒杀两样叠着来。
- 对比：用 MQ 当 RPC 同步等结果，超时和积压会反噬用户请求。
- 加码：死信队列修 poison message。无限重试会把分区卡住。Kafka 分区有序，全局 FIFO 做不到。

## 代码 / 例子

```text
# 生产者：同步 confirm / Kafka acks=all
publish order.created {id:88}  # wait ack

# 消费者
if !insert_dedup(msg.id): ack; return
update_points(order_id=88)
ack
# 失败 n 次 → DLQ
```

## 常见追问

- Q: 怎么保证消息不丢、不重复？
  A: 不丢：生产者等待 broker ACK（Kafka `acks=all`，多副本 ISR）；broker 持久化；消费者处理成功后再 ACK，关闭自动 ACK。重复没法从投递上消灭（至少一次和恰好一次成本差一个数量级），消费幂等让重复变得无害。恰好一次要事务消息 + 幂等，Kafka 事务也只保证「生产到分区」这一段。
- Q: 积压了几百万条消息怎么快速处理？
  A: 先看原因：消费者挂了、处理变慢、下游 DB 扛不住、死循环重试。扩消费者（分区数不够先加分区，Kafka 加分区会打乱哈希要谨慎）；临时跳过非核心逻辑；修 bug 后用更多实例刷积压；过期的可以直接丢或进冷存储。削峰队列积压是预期，要有积压告警和最大延迟 SLO。

## 自己的易错点 / 之前答崩过的地方

- 消费一进来就 ACK，进程一杀消息没了。
- 用 MQ 当 RPC：同步等消费结果，把超时和积压耦合进用户请求。
- 多分区还要求全局 FIFO，做不到，除非单分区并接受吞吐上限。
