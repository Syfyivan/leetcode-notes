# CAP与BASE

## 核心回答（面试口述版，1 分钟能讲完）

CAP 说：网络分区发生时，分布式系统在一致性 C 和可用性 A 里只能保一个，分区容忍 P 是广域网的现实。C 这里指线性一致：一次写，后续读立刻看到。A 指每个非故障节点都给响应。单机数据库看起来 CA，是因为它没有分区这个维度。工程上 ZK / etcd 偏 CP，老版 Eureka 偏 AP。BASE 是 AP 方向的补丁：基本可用、软状态、最终一致，用补偿把短窗口的不一致收齐。

## 展开

1. CAP 三者为什么不能同时满足

   分区把节点切成两坨。若保证 C，少数派不能继续写，表现为不可用。若保证 A，两坨都接写，数据分叉，C 没了。没有分区时 C 和 A 可以同时有，于是很多人说「CA 系统」，其实是单机或忽略 P。PACELC 补充：没分区时还要在延迟 L 和 C 之间选。

2. CP 和 AP 的实际取舍（ZK vs Eureka）

   ZooKeeper / etcd：多数派选举，少数派拒绝写，配置、分布式锁选它。
   Eureka：节点彼此失联仍返回本地缓存的注册表，服务发现宁可脏，也不能全体连不上。
   Redis Cluster：槽位迁移时部分 key 可能 `MOVED`，设计偏可用 + 最终哈希槽一致。
   业务：库存扣减偏 C，首页推荐列表偏 A。

3. BASE：基本可用、软状态、最终一致

   Basically Available：故障时降级，不把整个站点 500。
   Soft state：允许副本暂时不同。
   Eventually consistent：停止写入后，副本会收敛。落地靠：消息重试、对账任务、CRDT、读修复、写时读主。一致从同步事务换成异步过程，仍然要有收敛路径。

## 延伸

- 相关题：主从复制。半同步缩小丢数窗口，读从库仍可能旧。这就是保 A 还是保 C。
- 对比：没有分区时延迟和一致仍要选。PACELC 把这句补上。
- 加码：库存扣减偏 CP，首页推荐偏 AP。按接口说，别给整个系统贴一个字母。

## 代码 / 例子

```text
# CP：etcd 选主，少数派
put /config/switch on    # 多数派 ack 才返回

# AP 最终一致：下单
INSERT order; publish order.created;
# 积分服务稍后消费，对账 job 每晚补齐漏单
```

## 常见追问

- Q: 分区一定会发生吗？为什么说 CA 系统不现实？
  A: 机房光纤、交换机、GC 长时间 STW、进程假死，对观察者都像分区。只要系统跨进程跨机器，P 就必须处理。自称 CA 的系统要么其实是单机，要么分区时脑裂（两边都写），要么分区时全体不可用（等于没保 A）。多机部署还想无视 P，故障时行为未定义。
- Q: 最终一致性在业务上怎么落地？
  A: 写后读走主库或带版本；跨服务用事务消息 / 出箱模式保证「落库和发消息」同成败；消费者幂等；定时对账把差额补上；用户可见文案写成「处理中」而不是立刻成功。支付回调、库存同步都是这套。

## 自己的易错点 / 之前答崩过的地方

- 把 CAP 的 C 说成 ACID 的 C。一个是副本线性一致，一个是业务不变式。
- 说「我们系统满足 CAP」。三个字母同时在分区下不成立。
- 把最终一致理解成可以随便丢更新。要有收敛路径，否则叫丢失。
