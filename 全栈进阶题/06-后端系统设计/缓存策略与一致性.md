# 缓存策略与一致性

## 核心回答（面试口述版，1 分钟能讲完）

业务里最常见的是 Cache Aside：读时先 Redis，miss 再查库并回填；写时先更新数据库，再删缓存。先删缓存再更库容易把旧值又写回去。删失败就多留一会儿脏数据，用重试或订阅 binlog 补偿。要求更强一致就缩短 TTL、对写入路径加锁，或直接读主库。缓存和 DB 同时在线做不到完美实时一致，只能把窗口收短。

## 展开

1. Cache Aside / Read Through / Write Through / Write Back

   - **Cache Aside**（旁路）：应用管缓存。读 miss 自己回填；写更新存储再让缓存失效。Redis 最常见。
   - **Read Through**：应用只问缓存，miss 由缓存组件加载 DB。
   - **Write Through**：写缓存时同步写 DB，两边都成功才返回。
   - **Write Back**：只写缓存，异步刷 DB。吞吐高，掉电丢数据，Redis 当主存储才考虑。

2. 更新时先删缓存还是先更库

   推荐 **先更库，再删缓存**。若先删缓存：A 删完，B 读 miss 把旧 DB 值填回，A 才把新值写入 DB，缓存脏了很久。先更库再删：最坏是删缓存失败，短时间读到旧值，下次读仍旧；TTL 会救。先更库再 **写** 缓存也不好：两个写者乱序会把老值覆盖新值。失效比更新安全。

3. 延迟双删、订阅 binlog 保证一致性

   延迟双删：先删 → 更库 → sleep 几百毫秒再删，挡住「更库前有人把旧值填回」的窗口。sleep 难调，还拖慢写。
   更干净：Canal / Maxwell 订 MySQL binlog，异步删或更新对应 key，应用写路径只打 DB。结合短 TTL。
   并发读写不一致：对同一个 key 的回源加互斥（见击穿），或用版本号，缓存里带 `version`，回填时 CAS。

## 延伸

- 相关题：缓存穿透击穿雪崩。回源路径要带互斥或逻辑过期，否则 Cache Aside 自己打穿 DB。
- 对比：Write Back 吞吐高，掉电丢数据。Redis 当缓存别走这条。
- 加码：回填用 `SET NX` 或带版本 CAS，避免 DEL 之后又被旧值 SET 回来。

## 代码 / 例子

```text
# Cache Aside 写
UPDATE item SET price=99 WHERE id=9;
DEL item:9                 # 失败则丢重试队列

# 读
GET item:9
# miss → SELECT → SET item:9 json EX 600
```

## 常见追问

- Q: 先更库再删缓存，删失败了怎么办？
  A: 写 Redis 失败不能当成功返回就完了。本地重试几次；仍失败把 `key` 丢给消息队列保证最终删掉。订阅 binlog 的删除是第二道。最差靠 TTL，例如 10 分钟内脏读。钱和库存别靠这套，直接走 DB 或带版本号的强一致存储。
- Q: 怎么应对缓存和数据库的并发读写不一致？
  A: 经典脏填：A 更库，B miss 读到旧行并 SET 缓存，A 再 DEL。若 B 的 SET 发生在 A 的 DEL 之后，缓存脏到 TTL。对策：DEL 在事务提交后；binlog 删除在 B 的 SET 之后再来一次；回填用 `SET key json EX 600 NX` 或带版本比较；热点 key 逻辑过期不主动 DEL。没有银弹，把窗口和业务容忍度说清楚。

## 自己的易错点 / 之前答崩过的地方

- 写路径「更新缓存」而不是删，并发写把旧对象 SET 上去。
- 缓存和 DB 的字段集合不同步，部分更新后 JSON 缺字段。
- 为了一致上分布式事务套 Redis 和 MySQL，复杂度和故障率比脏读几秒更差。
