# 事件循环与浏览器的区别

## 核心回答（面试口述版，1 分钟能讲完）

Node 的事件循环是 libuv 的六阶段循环，浏览器是 HTML 规范里的宏任务 / 微任务两层。口述抓住三句：Node 一轮循环按 timers → pending callbacks → idle/prepare → poll → check → close callbacks 走；每个阶段切走之前会把 `process.nextTick` 队列清空，再跑 Promise 微任务，nextTick 比 Promise 更优先；`setTimeout(fn, 0)` 进 timers，`setImmediate` 进 check，两者谁先跑要看是不是在 I/O 回调里。

## 展开

1. Node 事件循环的六个阶段（timers/pending/poll/check/close 等）

   libuv 每轮循环固定走这些阶段：
   - **timers**：到期的 `setTimeout` / `setInterval` 回调
   - **pending callbacks**：上一轮推迟的 I/O 回调，典型是 TCP 的 `ECONNRESET` 这类系统错误
   - **idle, prepare**：libuv 内部用，业务碰不到
   - **poll**：取新的 I/O 事件并执行回调。没到期 timer、也没 `setImmediate` 时，这里会 `epoll_wait` / `kevent` / `IOCP` 阻塞等 I/O
   - **check**：`setImmediate` 回调
   - **close callbacks**：`socket.destroy()` 之后的 `'close'`

   fs、net、DNS（除 `dns.lookup` 走 `getaddrinfo` 线程池）的完成回调大多在 poll 阶段进来。CPU 密集别堵在主线程，否则整轮循环转不动。

2. process.nextTick 和 微任务队列的优先级，和 Promise 谁先执行

   阶段切换时 Node 会先清空 nextTick 队列，再清空微任务（`Promise.then` / `queueMicrotask`）。所以同一轮里 `process.nextTick(fn)` 一定先于 `Promise.resolve().then(fn)`。nextTick 不属于 libuv 阶段，是 V8 / Node 自己插的。递归 `nextTick` 会让 poll 永远进不去，I/O 被饿死。

3. 浏览器只有宏/微两层，Node 为什么要分阶段

   浏览器一轮大致是：取一个宏任务（script / timer / I/O / UI）→ 清空微任务 → 有机会渲染。Node 面对的是文件、socket、线程池，要把「到期定时器、阻塞等 I/O、立刻要跑的 Immediate、关连接」拆开，避免在 poll 里无限等的同时饿死 timer。分阶段是给 I/O 模型用的调度，不是多出来的概念。

## 代码 / 例子

```js
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
// 主模块输出：nextTick → promise；timeout / immediate 顺序不确定

const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// I/O 回调里一定是 immediate → timeout：poll 结束立刻进 check
```

## 常见追问

- Q: setTimeout(fn,0) 和 setImmediate 谁先执行？为什么不确定？
  A: 主模块里不确定。脚本跑完才进循环，timers 阶段看 0ms 定时器有没有被记成到期，和启动耗时、时钟精度有关。I/O 回调里确定：当前在 poll，下一阶段就是 check，`setImmediate` 先跑，`setTimeout(0)` 要等下一轮 timers。面试就答这两句。
- Q: process.nextTick 用多了会有什么问题（饿死 IO）？
  A: nextTick 在阶段之间会抽干。回调里再 `nextTick`，poll 进不去，`epoll_wait` 没机会，文件和 socket 回调全挂着。递归 Promise 微任务也一样会饿死。需要推迟又不想饿死 I/O 时用 `setImmediate`。

## 自己的易错点 / 之前答崩过的地方

- 把浏览器的「宏任务」直接套到 Node：Node 没有单一宏队列，timer、poll、check 是分开的。
- 以为 `setTimeout(0)` 等于立刻执行。最小延迟在浏览器曾被钳到 4ms，Node 也受 poll 阻塞和系统定时器分辨率影响。
- 把 `process.nextTick` 说成「下一轮 tick」。它是当前阶段结束前插队，比下一轮早得多。
- `dns.lookup` 走 libuv 线程池（`getaddrinfo`），`dns.resolve` 走 c-ares 网络 I/O，卡 lookup 会占满 `UV_THREADPOOL_SIZE`（默认 4）。
