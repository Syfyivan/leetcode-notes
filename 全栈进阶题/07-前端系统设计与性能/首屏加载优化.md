# 首屏加载优化

## 核心回答（面试口述版，1 分钟能讲完）

首屏慢就三刀：体积、请求、渲染。体积靠拆包、tree-shaking、压缩（gzip/brotli）、图片 webp。请求靠 CDN、HTTP/2 多路复用、`preload` 关键字体和 LCP 图、少域名。渲染靠尽快出 HTML：SSR / 流式渲染、骨架屏、关键 CSS 内联，JS 用 `type=module` + `defer` 别堵 HTML 解析。指标看 LCP（最大内容绘制），不是单纯 window.onload。

## 展开

1. 资源体积（拆包、tree-shaking、压缩）

   路由级 `import()` 拆出后台页。moment 换 dayjs，按需引入 lodash-es。生产 `terser` + gzip，nginx `brotli`。图片：正确尺寸、webp/avif、`srcset`。包体积用 `rollup-plugin-visualizer` 看哪块肥。

2. 请求优化（预加载、HTTP2、CDN）

   静态资源 CDN，HTML 短缓存或协商缓存。HTTP/2 不必再强行 sprite / 域名散列。`<link rel="preload" as="image">` 给 LCP 图；`preconnect` 给 API 域。`prefetch` 给下一页，别和 preload 抢带宽。字体 `font-display: swap` 避免文字不可见。

3. 渲染优化（SSR、骨架屏、关键 CSS）

   CSR 要等 JS 下载执行才有内容，白屏长。SSR 首包就是带正文的 HTML，爬虫和 LCP 都受益。骨架屏让布局先稳住，降 CLS。关键 CSS 内联在 `<head>`，其余异步。`content-visibility` 给首屏外模块。

## 延伸

- 相关题：SSR 与同构渲染。营销页值得 SSR，控制台 CSR 就够。
- 对比：`preload` 抢当前带宽，`prefetch` 给下一页。全路由 prefetch 会抢走 LCP。
- 加码：LCP 图不要 `loading=lazy`，那是把最大元素主动推迟。HTTP/2 之后不必再域名散列、CSS sprite。

## 常见追问

- Q: SSR 为什么能优化首屏？它的代价是什么？
  A: HTML 里已经有文字和图片地址，浏览器不用等 JS 就能画，TTFB 到 FCP / LCP 的间隙短，SEO 也有文档。代价：Node 要渲染，TTFB 可能变长；要防内存泄漏；hydration 要匹配，否则闪一下；缓存和 Cookie 个性化打架。不是所有页都值得 SSR，营销页、文档适合，后台控制台 CSR 就够。
- Q: 路由懒加载和组件懒加载怎么做？
  A: 路由 `component: () => import('./X.vue')`，Webpack / Vite 打出独立 chunk，切到这条路由才下载。组件级用 `defineAsyncComponent` / `React.lazy` + `Suspense`。注意把首屏按钮所需的 chunk 仍留在主包，别把首屏也懒到二次请求。魔法注释 `/* webpackPrefetch: true */` 给高概率下一页。

## 自己的易错点 / 之前答崩过的地方

- 把所有路由 prefetch 了，首屏带宽被后台页抢走。
- 图用 3x 原图再 CSS 缩小，LCP 资源 4MB。
- 只盯 `bundle.js` 大小，忽略第三方字体和未压缩的 banner 图。
