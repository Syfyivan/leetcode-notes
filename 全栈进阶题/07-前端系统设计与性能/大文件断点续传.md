# 大文件断点续传

## 核心回答（面试口述版，1 分钟能讲完）

大文件切成片（`Blob.slice`），每片 2~5MB，并发 3~4 路上传。秒传：先算整个文件 hash，服务端有这个 hash 就直接返回 URL。断点：服务端告诉哪些 chunk 已经到了，客户端跳过，只补缺的。全部到齐后调合并接口，服务端按序号 `cat` 成原文件。失败的分片单独重试，合并只认序号，不认到达顺序。

## 展开

1. 分片（slice）+ 并发上传 + 合并

   `const chunk = file.slice(i * size, (i + 1) * size)`。每片带 `hash`、`index`、`fileHash`。上传 `PUT /chunk` 或 `POST FormData`。并发池（见手写调度器）：同时在飞不超过 4 路，结束一个补一个。服务端把片落到 `tmp/fileHash/0`, `1`, ... 合并时按数字序写目标。

2. 断点续传（记录已传分片 hash）

   续传前 `GET /upload/status?fileHash=` 返回已到达的 index 数组。本地也能用 IndexedDB 记成功片，刷新页面先问服务器为准。下载侧断点是 HTTP `Range` / `206 Partial Content`，和上传是两套。

3. 秒传（文件 hash 秒级比对）

   上传前 `POST /check { fileHash, name, size }`。命中则 200 带 url，0 带宽。hash 用 SparkMD5 / SHA-256。整文件读进内存会卡死，按片 `FileReader` 增量 `md5.append(buf)`。

## 代码 / 例子

```js
async function plan(file, size = 4 * 1024 * 1024) {
  const chunks = [];
  for (let i = 0; i < file.size; i += size) {
    chunks.push(file.slice(i, i + size));
  }
  const fileHash = await hashFile(file); // worker 里增量 md5
  const { exists, uploaded } = await check(fileHash);
  if (exists) return { url: exists };
  const rest = chunks.map((c, i) => ({ c, i })).filter((x) => !uploaded.includes(x.i));
  return { fileHash, rest };
}
```

## 常见追问

- Q: 文件 hash 太大算得慢怎么办（抽样/web worker）？
  A: 计算丢 Web Worker，主线程只画进度。仍慢就抽样：头 2MB + 尾 2MB + 中间均匀 N 块做 hash，冲突概率略升，秒传够用；真正去重仍以服务端完整 hash 为准，可在合并后再算一遍。WASM 版 hash 比纯 JS 快。超大文件给用户看「校验中 30%」，别让页面假死。
- Q: 分片上传失败怎么重试、怎么保证顺序？
  A: 单片失败放回队列，指数退避，最多 3 次。并发完成顺序是乱的，合并时按 index 排，缺号就拒绝合并。服务端对 `(fileHash, index)` 做幂等，重复上传覆盖或 200。最后一片到了并不等于齐了，要以 status 接口的齐全为准再 merge。

## 自己的易错点 / 之前答崩过的地方

- 用 `readAsArrayBuffer` 读整个 2GB 文件再切片，内存直接顶爆。必须 `file.slice`。
- 合并接口没做权限和大小校验，临时目录被扔垃圾片。
- 只在 localStorage 记进度，换浏览器或清缓存就全部重传，服务器其实已经有片。
