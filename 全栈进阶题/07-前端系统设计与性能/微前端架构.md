# 微前端架构

## 核心回答（面试口述版，1 分钟能讲完）

微前端把巨石拆成可独立发版的子应用，基座管路由、登录、公共依赖，子应用管自己的页面。图方便技术栈可以不同，但成本是隔离、重复依赖、体验缝。落地两派：qiankun（HTML entry，加载子应用 HTML 再跑 JS）；Module Federation（构建期共享模块，运行时拉 remoteEntry）。隔离要解决 JS 全局污染和 CSS 打架，通信用 props / EventBus / 共享 store，别直接改对方 window。

## 展开

1. 为什么要微前端（巨石应用拆分、技术栈无关）

   多团队抢一个 repo 发版、老 Vue2 插新 React 页、局部重写。独立部署是真需求。如果只是代码模块化，monorepo + 组件库就够，不必上微前端。

2. 主流方案（qiankun/module federation）

   - **qiankun**：基于 single-spa。子应用导出 `bootstrap/mount/unmount`。基座 `registerMicroApps`，按路由 load。HTML entry 让子应用自己的 webpack publicPath 较自然。
   - **Module Federation**：Webpack 5。host 运行时 `import('app2/Header')`。适合同一技术栈共享组件，粒度比「整应用」细。
   - iframe：隔离最强，体验和通信最差，后台嵌套旧系统还在用。

3. JS 沙箱、样式隔离、应用通信

   JS：快照沙箱（进子应用前记下 window，离开恢复），Proxy 沙箱（每个应用一个 fakeWindow，激活时把代理当全局）。qiankun 单实例用 snapshot，多实例用 proxy。
   CSS：动态 stylesheet 随应用挂卸；`experimentalStyleIsolation` 给选择器加前缀；Shadow DOM 最硬，坑是弹层 `document.body`。
   通信：基座 props 下发登录态；`initGlobalState`；自定义事件。少用全局变量。

## 延伸

- 相关题：模块机制。MF 的 `shared singleton` 和 Node 的 `require.cache` 是同一类「只加载一份」。
- 对比：iframe 隔离最强，通信和体验最差；qiankun 加载整应用，MF 分享组件粒度更细。
- 加码：两个子应用各打一份 React，hook 会报错。`shared` 必须 singleton。三个页面三个应用，首屏会串行加载三个 runtime。

## 代码 / 例子

```js
registerMicroApps([{
  name: 'shop',
  entry: '//localhost:7100',
  container: '#subapp',
  activeRule: '/shop',
  props: { token },
}]);
start({ sandbox: { experimentalStyleIsolation: true } });
```

## 常见追问

- Q: qiankun 的 JS 沙箱是怎么做隔离的？
  A: 激活子应用时，用 Proxy 包一层 window，子应用的 `window.xxx = 1` 写在 fakeWindow 上。切走时不用它，全局看起来没被污染。改 `window.location` 这类不能代理的还是会漏。快照模式则是进出时 diff window 的可枚举属性。都不能挡住对 `document` 的直接操作，所以不是安全沙箱，只是尽量恢复现场。
- Q: 微前端的样式冲突怎么解决？
  A: 约定 BEM / CSS Modules / 各应用前缀。qiankun 实验性隔离会把子应用选择器改写成 `.shop-hash h1`。Shadow DOM 物理隔离，但弹出层、全局 toast 要挂到 shadow root。公共组件抽到基座，避免两份 antd 主题互覆盖。动态插入的 style 标签要在 unmount 时删掉。

## 自己的易错点 / 之前答崩过的地方

- 两个子应用各打一份 React 16 和 18，运行时 hook 报错。MF 要 `shared: { react: { singleton: true } }`。
- 路由基座用 history，子应用用 hash，刷新 404。约定一种，nginx 回退 index.html。
- 为拆而拆，三个页面三个应用，首屏串行加载三个 runtime。
