# 分布式锁

## 核心回答（面试口述版，1 分钟能讲完）

单 Redis 实例上的锁：`SET lock:order:1 <uuid> NX PX 30000`，NX 保证只有一个人种上，PX 避免进程挂了锁永不释放。解锁必须校验 uuid 再用 Lua 删，防止误删别人的锁。业务比 TTL 长时用看门狗续期（Redisson 默认 30s 锁，10s 续一次）。主从异步复制时，锁写入主库还没到从库、主库挂了，另一客户端能在新主上再拿到锁，所以这把锁是「够用的互斥」，不是线性一致的。Redlock 试图在 N 个独立实例上多数派加锁，争议很大，校招说清楚风险比背算法重要。

## 展开

1. SETNX + 过期时间的基础实现

   老写法 `SETNX` + `EXPIRE` 不是原子的，进程死在两句之间锁就永远在。一条 `SET key value NX PX ttl` 解决。value 必须是随机数，不能只存 1。

2. 误删问题（value 存唯一标识）、锁续期（看门狗）

   客户端 A 超时，锁被 Redis 过期掉，B 拿到锁。A 业务回来执行 `DEL`，会把 B 的锁删掉。所以删除脚本：

   ```text
   if redis.call('GET', KEYS[1]) == ARGV[1] then
     return redis.call('DEL', KEYS[1])
   else return 0 end
   ```

   续期：业务侧起守护线程，锁还在且 value 是自己的就 `PEXPIRE`。Redisson 的 `watchdog` 是这个。进程被 kill -9，看门狗也没了，只能等 TTL。锁的粒度按业务键，不要一把全局 lock。

3. Redlock 的争议

   Antirez 提出：5 个独立 Redis，对多数成功加锁且耗时 < TTL 才算成功。Martin Kleppmann 指出时钟跳变、GC 停顿、网络分区下仍可能两把锁同时有效。生产里多数团队：单主 + 可接受极低概率双持；真要强互斥用 etcd / ZooKeeper 的租约（session + fence token）。fencing token：每次加锁单调递增，写存储时带 token，旧 token 被拒。

## 延伸

- 相关题：幂等性设计。锁防并发，唯一键防重试。钱相关两样都要。
- 对比：击穿用的那把 `SET NX` 和这把锁是同一句命令，粒度一个按缓存 key，一个按业务。
- 加码：主从切换会丢锁，和复制延迟是一类问题。持久化救不了这个窗口。钱相关用 DB 唯一约束或 etcd。

## 代码 / 例子

```text
SET lock:sku:9 7f3a NX PX 10000
# ... 业务 ...
EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end" 1 lock:sku:9 7f3a
```

## 常见追问

- Q: 锁过期了业务还没执行完怎么办？
  A: 续期（看门狗），或一开始把 TTL 设得比最坏业务时间长。续期失败要立刻停业务，不能删锁后还写库。更严的是fencing：拿到锁顺便拿一个递增 token，写 DB 的 WHERE 带 `token >= old`，即使双持，旧持有者写不进去。
- Q: 单机 Redis 锁在主从切换时会失效吗？
  A: 会。锁在主上 `SET` 成功，binlog/repl 还没到从，主宕机，从升主没有这把锁，第二个客户端 `SET NX` 成功。半同步能缩小窗口，不能消掉。Cluster 迁槽期间也有类似问题。所以 Redis 锁适合防重复点击、库存不太极端的互斥；钱相关用 DB 唯一约束或 ZK/etcd。

## 自己的易错点 / 之前答崩过的地方

- 解锁只 `DEL`，不比对 uuid，误删别人锁。
- 用 `SETNX` + 过期两条命令，崩溃留下死锁。
- 把 Redlock 讲成「业界标准」。面试官能立刻拿 Kleppmann 的文章来问。
- 锁住了读-改-写的库存，却忘了 Redis 锁成功后 DB 更新还要事务或乐观版本号。
