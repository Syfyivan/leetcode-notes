# 缓存穿透击穿雪崩

## 核心回答（面试口述版，1 分钟能讲完）

三个词别混。穿透：查根本不存在的数据，缓存没有、库也没有，请求每次打穿到 DB，恶意扫 ID 最常见。击穿：一个热点 key 过期，瞬间并发都去打 DB。雪崩：大批 key 同时过期，或 Redis 挂了，DB 被集体打满。对策分别是：空值缓存 / 布隆过滤器；互斥锁或逻辑过期；TTL 加随机抖动、Redis 高可用、接口限流降级。

## 展开

1. 三者的定义区别

   | | 对象 | 缓存状态 | DB |
   | --- | --- | --- | --- |
   | 穿透 | 不存在的数据 | 一直 miss | 每次都查，结果空 |
   | 击穿 | 单个热点 key | 刚好过期 | 并发打进来 |
   | 雪崩 | 大量 key 或整实例 | 同时失效 / 不可用 | 流量整体压上 |

2. 穿透→布隆过滤器/空值缓存

   空值：DB 没有也 `SETEX key 30 ""`，挡住重复穿透，TTL 短，避免长期脏空。
   布隆：把存在的 ID 放进 Bitmap 多哈希，查询前先问「可能存在吗」。有假阳性（说有其实没有，会落到 DB），没有假阴性（说没有就真没有）。删除难，用 Counting Bloom 或定期重建。参数乱的 ID 在布隆直接拒。

3. 击穿→互斥锁/逻辑过期；雪崩→过期时间打散

   击穿：
   - 互斥：只有一个线程 `SET lock NX PX 1000` 成功才回源，别人稍等再读缓存。简单，失败点是锁过期和惊群。
   - 逻辑过期：value 里塞 `expireAt`，过期仍返回旧值，后台异步刷新。用户无感，要接受短暂脏读。
   雪崩：TTL = base + random(0, 300)；多级缓存；Redis 主从 + Cluster；熔断，DB 扛不住就返回底图 / 默认值。Redis 挂和 TTL 一起到期是两类雪崩，高可用解前一类。

## 延伸

- 相关题：缓存策略与一致性。击穿锁和 Cache Aside 回源是同一条路径。
- 对比：雪崩有两类，TTL 一起到，和 Redis 挂了。高可用只解后一类。
- 加码：布隆说「没有」可以信，说「有」仍可能打到 DB。假阳性再接一层短 TTL 空值缓存。

## 代码 / 例子

```text
# 空值缓存
GET item:999          # miss
# SQL 无记录
SETEX item:999 30 ""

# 击穿互斥（伪代码）
SET lock:item:1 1 NX PX 1000
# 成功则查库 SET item:1 json EX 600
# 失败则 SLEEP 50ms 再 GET
```

## 常见追问

- Q: 布隆过滤器为什么会误判？怎么删元素？
  A: 多个哈希函数映射到同一段位图，不同元素可能把同样的位置 1，查询时这些位都是 1 就以为存在。误判率和位图长度、哈希个数、元素数有关。标准布隆不能安全删除：把位置 0 可能伤到别人。方案：Counting Bloom 每位一个计数器；或 RedisBloom 的 Cuckoo Filter；或业务上定期用全量 ID 重建。
- Q: 热点 key 击穿的互斥锁方案有什么问题？
  A: 拿到锁的线程挂了或回源太慢，锁 TTL 到了别人又打进 DB，形成小惊群。锁粒度太大（整把大锁）把不相关的 key 也串行了。Redis 单线程，热点 key 还可能把带宽打满，这是「热 key」问题，要用本地缓存（Caffeine）+ 分片复制，不只是击穿锁。逻辑过期没有这个等待，但会把过期数据再卖一会儿。

## 自己的易错点 / 之前答崩过的地方

- 穿透、击穿、雪崩三个定义张冠李戴，尤其击穿和雪崩。
- 空值缓存 TTL 设成和正常数据一样长，商品一旦上架还显示没有。
- 只在应用层加锁，多实例各自一把 JVM 锁，挡不住。锁必须在 Redis 上。
