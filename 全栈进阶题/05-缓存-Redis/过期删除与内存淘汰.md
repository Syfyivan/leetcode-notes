# 过期删除与内存淘汰

## 核心回答（面试口述版，1 分钟能讲完）

过期键走两条路：访问时惰性删除；后台定时抽 20 个带 TTL 的键，过期就删，循环直到超时比低于 25% 或跑完时间片。内存到 `maxmemory` 后按策略淘汰，常见 `allkeys-lru` 和 `volatile-lru`。没开淘汰且内存满，写命令返回 `OOM`。过期和淘汰不是一回事：过期是 TTL 到了，淘汰是内存不够了。

## 展开

1. 惰性删除 + 定期删除

   惰性：`GET` 发现 `now >= expire` 就删并返回 nil。不访问的键会一直占着，直到定期任务或淘汰碰到它。
   定期：serverCron / hz 次每秒，从 expires 字典随机抽 20 个，删过期的。如果过期比例 > 25%，再抽一轮，直到用完时间片。全量扫 expires 在键百万时会堵单线程，所以抽样。

2. 八种内存淘汰策略（LRU/LFU/random/ttl）

   - `noeviction`：写报错，默认值。
   - `allkeys-lru`：所有键里淘汰最近最少用。
   - `volatile-lru`：只在设了 TTL 的键里 LRU。
   - `allkeys-lfu` / `volatile-lfu`：最少使用频率（Redis 4+）。
   - `allkeys-random` / `volatile-random`：随机。
   - `volatile-ttl`：TTL 越近越先踢。

   LRU 不是精确链表，是采样 N 个（`maxmemory-samples` 默认 5）挑空闲时间最大的，近似 LRU。LFU 用 16bit 计数衰减。

3. maxmemory 打满会怎样

   达到上限后，写请求先按策略腾地方。腾不出来（`noeviction`，或 volatile 策略但没有 TTL 键）就 `OOM command not allowed`。读一般仍可。主从场景要给 replica 留同一套 maxmemory，避免主踢从没踢导致不一致。过期键在从库上是懒处理的，主库 DEL 会传到从库。

## 代码 / 例子

```text
CONFIG SET maxmemory 2gb
CONFIG SET maxmemory-policy allkeys-lru
SET k1 v EX 10          # 10 秒后惰性或定期删
INFO memory             # used_memory, evicted_keys
INFO stats              # expired_keys
```

## 常见追问

- Q: 定期删除为什么是随机抽样而不是全扫？
  A: Redis 命令处理是单线程（6.0 后 IO 有额外线程，过期仍在主线程）。expires 字典几百万条，全扫一次延迟直接上十毫秒。随机 20 个能把过期比例收敛到 25% 以下，剩下的靠惰性补。极端情况大量键同一时刻到期，定期删不过来，会靠惰性和淘汰顶一阵，P99 会抖。
- Q: allkeys-lru 和 volatile-lru 区别？
  A: `allkeys` 从全部键挑牺牲品，适合 Redis 当纯缓存，没 TTL 的也能踢。`volatile` 只踢带过期时间的，适合「一部分缓存、一部分要持久的数据」混部。混部其实危险，缓存把内存打满时 volatile 若没 TTL 可踢，写仍然 OOM。当缓存集群用 `allkeys-lru` 更干净。

## 自己的易错点 / 之前答崩过的地方

- 以为 TTL 一到键立刻消失。没人访问又没抽到，它还在 `INFO keyspace` 里。
- 把淘汰策略当成过期策略。键没 TTL 时 `volatile-*` 等于不淘汰。
- 把 Redis 当数据库还不设 maxmemory，机器内存被撑到开 swap，延迟尖刺。
