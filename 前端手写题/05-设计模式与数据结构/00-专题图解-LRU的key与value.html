LRU 的钥匙与包裹

key 和 value 到底各存什么？一句话：key 是「怎么找」，value 是「找到了给你什么」。下面用一个快递柜、一张名册、一条会动的队伍，把它彻底讲透。

KEY 存的是

查询编号——取包裹的取件码、查人的身份证号。它唯一，是你下次来认领数据的凭证。

VALUE 存的是

数据本身——柜子里的包裹、字典里的释义。get(key) 最终还到你手里的就是它。

01

先想一个快递柜

LRU 缓存就是一个容量有限的快递柜：格子就那么多（容量 capacity），存满了必须清一格才能放进新包裹。清哪格？LRU 的规矩很现实——谁最久没人碰，就清谁（Least Recently Used，最久未使用）。

put(key, value)存包裹：把 value（包裹）塞进柜子，登记一个 key（取件码）。key 已存在就是换新包裹。
get(key)报取件码取包裹：包裹只是被看了一眼，并不搬走（下次还能 get），但这一格立刻被标记成「刚用过」。
柜子满了把最久没人 get 也没人 put 的那格清空，腾给新包裹，名册上同步划掉它。
key 是取件码，value 是包裹。码必须唯一，包裹随便多大。
02

真实项目里，它们各是什么

脱离题目，工程里缓存无处不在——但不管什么场景，key 永远是「能唯一锁定一条数据的东西」，value 永远是「重新获取很贵，所以存下来的结果」：

缓存场景key 存什么value 存什么
用户信息缓存用户 ID："10086"{ name: "小明", level: 3 }
接口结果缓存"page=1&size=20"接口返回的那份 JSON
图片 / 资源缓存"/img/logo.png"图片的二进制内容
函数记忆化 memoize"fib(10)"（参数转的串）算好的结果 55
两条规律：key 要短、要唯一——它每次都要被拿去哈希计算；value 是大块头——它就是你缓存它的全部理由（重新算 / 重新请求太贵）。你笔记里的 memoize缓存.js 就是表格最后一行。
03

翻开实现：key 和 value 住在哪

上面是使用者视角。翻开标准实现（哈希表 + 双向链表），你会发现一件反直觉的事：key 存了两份，而名册的 value 位置住的根本不是包裹。

名册（哈希表 MAP）——只管「按 key 秒找到人」

2──▶② 的小纸条（指向节点的引用）
3──▶③ 的小纸条（指向节点的引用）
名册每行的「小纸条」，都拽着队伍里对应的那个节点 ↓
队伍（双向链表）——只管「记住谁旧谁新」，左旧右新

KEY 住两处名册的键 + 节点身上的「工牌」字段
VALUE 住一处真正的包裹，只住在链表节点怀里
名册的 VALUE不是包裹！是「节点的小纸条」（引用）
问名册的 value 为什么存「节点」，不直接存包裹？

get(key) 要一口气办两件事：①把包裹还给你；②把这格标记成「最新」。如果名册只存包裹，第②件事就得沿链表一格一格找节点，O(1) 秒变 O(n)。存节点引用，一张纸条两件事全办完。

问链表节点为什么还要「再」存一份 key？

淘汰是从 head 门岗右边踢人的，踢的时候手里只有节点；可名册划名只认 key。所以取件码必须当成工牌戴在节点身上，最后一刀才能落下去：map.delete(oldest.key)。

顺带一提：你笔记里的方案一（纯 Map 版），名册的 value 存的就是老老实实的包裹本身——因为「谁旧谁新」外包给了 Map 自己的插入顺序；方案二把顺序外包给手写链表，名册的 value 才变成「节点纸条」。两版对用户的 key / value 语义完全一样。

05

对照代码看

下面是你笔记里 LRUCacheLinked 的节选，标了 ①②③ 的地方就是 key / value 的安身之处：

LRUCacheLinked.js · 节选（注释略有改动）
class Node {
  constructor(key, value) {
    this.key = key;      // ① 工牌：被淘汰时拿去名册划名字用的
    this.value = value;  // ② 包裹：get 时真正还给用户的东西
    this.prev = null;
    this.next = null;
  }
}

class LRUCacheLinked {
  constructor(capacity) {
    this.map = new Map();  // ③ 名册：key → 节点的小纸条（不是包裹！）
    this.head = new Node(0, 0); // 空门岗，不存数据
    this.tail = new Node(0, 0);
  }

  get(key) {
    if (!this.map.has(key)) return -1;
    const node = this.map.get(key); // 名册 O(1) 点名
    this._moveToTail(node);        // 用过 = 抽出来接到队尾（变最新）
    return node.value;             // 还给用户的是 value
  }

  put(key, value) {
    if (this.map.has(key)) {         // 已有这号 → 换包裹 + 搬到队尾
      const node = this.map.get(key);
      node.value = value;
      this._moveToTail(node);
      return;
    }
    const node = new Node(key, value); // 节点身上 key、value 各带一份
    this.map.set(key, node);          // 名册登记：key → 节点
    this._addToTail(node);
    if (this.map.size > this.capacity) {
      const oldest = this.head.next;  // 门岗右边 = 最久没用
      this._remove(oldest);
      this.map.delete(oldest.key);  // ★ 节点身上那份 key 在这里用上了
    }
  }
}
06

常见追问

纯 Map 版为什么 delete 再 set 就算「变最新」？
JS 的 Map 按插入顺序排列。delete 再 set 等于把这条记录抽出来重新排到队尾——队尾就是最新。所以那版名册里 value 直接存包裹就够了，顺序由 Map 自己的白送功能管。
get 之后包裹会被「拿走」吗？
不会。缓存不是租借处——get 只是看了一眼并刷新新鲜度，包裹还在柜里，下次 get 还是它。这也是缓存和「队列消费」的本质区别。
两次 put 用同一个 key 会怎样？
算更新：包裹换新，这条记录跳到最新，总条数不变（不会占两格）。因为名册按 key 点名，一个 key 只能对应一条记录。
容量满了先踢谁？
head 门岗右边第一个——它是最久没被 get / put 碰过的。注意 LRU 只认「最近」，不认「资历」：存得早但最近被摸过的，照样活得好好的。
面试官问「为什么 get / put 都是 O(1)」，怎么答？
两套结构各干一件 O(1) 的事：哈希名册按 key 秒找到节点；双向链表摘下 / 接上一个节点只改几个指针。谁也不需要遍历，合起来每步操作都是常数级。
真实项目里 LRU 用在哪？
Redis 内存满了的淘汰策略之一、浏览器的资源缓存、Vue 的 keep-alive、图片库的内存缓存、HTTP/2 连接池……凡是「内存有限、又想让常用地数据留得久一点」的地方，都有它。

一句话带走：key 是「怎么找」，value 是「找到了给你什么」；名册按 key 秒定位，队伍按新旧排座次——两份 key（名册的键 + 节点的工牌）缺一不可。
